# Part A: engines and compilers built in demo images

## Summary (findings, no advice)

1. Every build in this group sits where its first commit put it, and in every case but Mojo's that was before packages existed: Neovim's chain on 2026-09-07 (`1f2954b6`, "Checkpoint source-built Neovim", no body), llama.cpp's two images on 2026-09-14 (`2a14ff91`, no body; the task: "`llama-build` retains reusable upstream libraries; `local-llm-build` compiles the C API adapter"), Codex's on 2026-09-09 (`95737c29`: "Keep the compiler and intermediate tools as reusable image stages"), Pi's on 2026-09-14 (`df46bc10`, "Separate JavaScript and Pi build producers from interactive images", no body). The shapes were kept through Dollyfile 6 and 7; the packages over them came on 2026-10-05 to 10-13 as `COPY` rows or views.
2. The three LLVMs are three revisions, not one source three ways: the seed's `4bfd08c2` (prints "24.0.0git"), Mojo's `4154b56c` (also "24.0.0git", 16 days and "2,381 commits" later, `mojo-compiler` task `:195-196`), and Rust's `52ed14fc` of `rust-lang/llvm-project` (prints "22.1.8"). The recorded reason for each own build: `llvm-cc` must give "the same bytes" as the seed compiler (`check.slop`, `Dollyfile-llvm-cc:86-119`); Mojo "is written against its pin … Not tried: compiling Mojo against the seed's revision" (`:220-226`); rustc's bootstrap accepts "need >=21" (`build/rustc-port/rust/src/bootstrap/src/core/build_steps/llvm.rs:634-638`), so 24 passes its check, and nothing records a try.
3. The three LLVM builds restate one configuration (`Dolly.cmake` at `llvm-build:47-69`, `rust-llvm:43-61`, `mojo-llvm:68-95`), share two patches by three staged copies with the same digests, and each is `FROM cmake-build` plus `INSTALL python` (as are `zero-ad-spidermonkey` and `meson`). They differ in projects (`clang;lld` / none / `clang;mlir`), PIC (Rust only), Zstandard (Mojo only), the default triple (Mojo's `wasm64-unknown-dolly`), and patches (Rust and Mojo add `llvm-main-executable`; Mojo adds `llvm-wait` and its own 75-line codegen patch). `make` took 2,502 s, 1,657 s and 3,925 s in this tree's logs.
4. "llama.cpp in `llama-build` and `local-llm-build`" is one build and one link: `llama-build` compiles llama.cpp, its `common` chat sources and ggml with the WebGPU backend (`:20-25`); `local-llm-build` compiles Dolly's two files and links them (`:25-27`). ggml is inside both engines' trees at different revisions: llama's ggml 0.23.0, transcribe.cpp's 0.25.3; of about 1,360 files 194 differ and 31 exist in one tree only. llama.cpp has `LLAMA_USE_SYSTEM_GGML` (`find_package(ggml)`); transcribe.cpp has no such switch (`add_subdirectory(ggml)` unconditionally, `CMakeLists.txt:439`).
5. The two ggml builds are built differently on purpose, as the recipes say: `speech-build` at `-O2 -pthread -msimd128` ("Threads and SIMD are what let the model keep up with speech", `:22`; measured: SIMD halves the model's time, speech task `:45`), `llama-build` at `-O1` without threads (the engine "links without `-pthread`", local-models `:224-226`).
6. `rust-build` "replaces the seed compiler in place twice" means: `compiler.slop` copies the rustc it built over `/opt/rust-sdk/bin/rustc-real` (`:41`), the file `rustc.sh` runs; `std.slop` deletes the 22 `.rlib` of the seed's standard library and copies its own (`:66-67`); both run twice (`:64-67`, `:71-73`), the second time by the first generation; the standard library the second builds must `cmp` equal (`:73`); the seed's Cargo then drives the Cargo build whose result replaces `/usr/bin/cargo` (`:80-81`). The owner chose this: "implement choice 1 for v0.1.1" (self-host-rust `:143-145`).
7. Neovim's Lua 5.1 is upstream's requirement, not the catalog's choice: Neovim's `CMakeLists.txt:187-193` looks for `luajit` or fails with "Failed to find a Lua 5.1-compatible interpreter", and the recipe's comment since the first module says "Neovim supports PUC Lua 5.1" (`1f2954b6:modules/lua.dm`). Nothing else links Lua 5.1 (`git grep`); utf8proc has a second user at another version (NetSurf's bundled 2.4.0 inside `wine-build`, Neovim's 2.11.3).
8. The rulings on record: 2026-10-05, "Lua 5.1 and libuv: private dependencies of Neovim and CMake, one consumer each through `FROM`" and "`llvm-tablegen`: a port that discovers requirements; nothing consumes it"; 2026-10-12, "`llama-build`, `local-llm-build`, `pi-local` | llama.cpp, `dolly-llama` | - | stay: one consumer, needs `gpu@0`", "utf8proc, tree-sitter, `liblpeg.a`, `libluv.a` | - | stay: portable C with one consumer", "Not a package: … a build stage (`*-build`, `rust-llvm`, `llvm-tablegen`)". `llama` became a view the next day (`edef36bc`).
9. Written out, a `llama-cpp` library package meets the host-module rule twice: `llama-build` declares no `gpu@0` and seals (archives stamp nothing), but `docs/dollyfile.md:216-218` says a library package declares "those every program built with it needs" (`sdl2`: `display@0`); a package that declared `gpu@0` could not be installed by `speech-build` or any microphone image (none declares it), and one that did not would leave `llama`'s `gpu@0` where it is today. Two flag sets (threads and SIMD, or neither) and two ggml revisions stand between one package and its two engines.
10. Not findable without building: whether llama.cpp `093a2f86` compiles against ggml 0.25.3 or transcribe.cpp against 0.23.0; whether rustc 1.98.1 or Mojo 1.1.0 compile against the seed's LLVM revision, or against one another's; the time and memory of a toolchain that `INSTALL`s a 428 MB LLVM instead of copying it; the build times of `pi-build`, `neovim-build` and `codex-build` in this tree (their logs hold no `time` rows).

## A4. What a shared package would look like, on real cases

Language facts used: a package keeps what it declares plus `COPY` results (`docs/dollyfile.md:200-202`); its `INSTALL` rows are installed first by whoever installs it (`:141-153`); a toolchain keeps the files of what it installs (`src/dollyfile.c:1401`); a library package "declares … those every program built with it needs" and `INSTALL` checks the installer declares them (`:216-219`); sealing scans retained executables, not archives (`:220-224`); `REQUIRES HOST` is never inherited (`:212-213`).

### (a) llama.cpp and ggml as a library package

What `llama-build` is today is already a library build with `EXPORTS`; what it is not is a package (role `TOOLCHAIN`, an `ENTRY`, kept by `FROM`). Written as one:

```text
DOLLY 7
PACKAGE llama-cpp
REQUIRES HOST runtime@0            # the archives stamp nothing: llama-build seals without gpu@0 (:3-8)
                                   # or: REQUIRES HOST gpu@0, by docs/dollyfile.md:216-218 (sdl2's shape)
FROM    /vX/demos/cmake/Dollyfile-cmake-build <sha>
REQUIRES TOOL cc c++ cmake make tar rm
SOURCE  /vX/dist/static/llama/source.tar <sha> /tmp/llama-source.tar
SLOP tar -xf /tmp/llama-source.tar -C /
SLOP cmake -S /tmp/llama -B /tmp/llama/build -DCMAKE_SYSTEM_NAME=Dolly … -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_FLAGS_RELEASE=-O1 …   # today's :20-23
SLOP cmake --build /tmp/llama/build --target llama ggml-webgpu llama-common
SLOP cmake --install /tmp/llama/build
EXPORTS LIB llama … llama-common … ggml … ggml-base … ggml-cpu … ggml-webgpu     # today's :28-33
EXPORTS HEADER llama /usr/include/dolly-llm
EXPORTS FOLDER llama-licenses /usr/share/licenses/dolly-llm
```

- **Then `local-llm-build`** cannot stay `FROM llama-build`; it becomes `FROM system-tools` (it needs `c++` only, `:12-14`) with `INSTALL llama-cpp`, and keeps the link `:25-27` unchanged; `llama` stays `FROM local-llm-build`, or holds the link itself (`FROM system-tools`, `INSTALL llama-cpp`, the one `c++` row) — in which case `amy install llama` would bring the six archives and headers along with `dolly-llama`, by the rule that a package's rows travel ([build-needs](../20261013-144754-build-needs/TASK.md)). `pi-local`'s two `COPY` rows become `INSTALL llama` either way (already possible today).
- **The host line.** `llama-build` declares no `gpu@0` and has built; so the archives carry no stamp and a package of them passes sealing with `runtime@0` alone. The doc's rule for libraries says otherwise ("`sdl2`: `display@0` and `input@0`"), and `edef36bc` gave `llama` its `gpu@0` because "default refuses it by that name". With `gpu@0` on the library, `speech-build` (hosts `:3-11`, no `gpu@0`) and the two microphone images (no `gpu@0` in `speech-to-text-mic` or `pi-phone`) could not `INSTALL` it (`:150-152`). Without it, a program linked with `-lggml-webgpu -ldolly-gpu` is refused at start unless its own image declares `gpu@0`, as the `mojo` package already accepts for its `gpu` library (`Dollyfile-mojo:18-19`). Both readings exist in the catalog today.
- **One build or two, for `speech`.** `speech-build` would use only `ggml`, `ggml-base`, `ggml-cpu`; but its ggml is 0.25.3 at `-O2 -pthread -msimd128` and llama's is 0.23.0 at `-O1` without threads. One package means one flag set for both: with threads, `dolly-llama` (today linked without `-pthread`, local-models `:224`) would link a threaded ggml-cpu (whether that stamps `threads@0` on the executable depends on what the link pulls; `docs/sources.md:73` ties `-pthread` to `threads@0`); without threads, speech loses what its recipe says keeps up with speech. And transcribe.cpp has no switch to take an external ggml (`add_subdirectory(ggml)`, `:439`), so sharing needs a change on the port's side there, where llama.cpp has `LLAMA_USE_SYSTEM_GGML`. A `ggml` package of its own (ggml-base, ggml-cpu, ggml-webgpu) that both engines install is therefore two changes away for speech (the CMake wiring, the flag set) and one revision question for llama (0.25.3 against `093a2f86`): not findable without building.
- **Simpler:** `llama-build` and `local-llm-build` collapse to a package and a link (two images to one package and one image, or one package); `pi-local`'s two `COPY` rows go; the pin of llama.cpp is written once. **More complicated or lost:** `llama-build`'s role as a `FROM` base (the engine link takes its libraries by `REQUIRES LIB`, which `INSTALL` satisfies); a session that installs `llama` may receive 6 archives it does not run; the `gpu@0` question above. **Who else could use it:** by the recipes, nobody but the engine; `speech` under the conditions above. **What would rebuild:** `llama-cpp` (294 s measured for the same build), `local-llm-build`, `llama`, `pi-local`, `dollyfile-studio` (`FROM pi-local`); the speech chain only if it switches.

### (b) An LLVM package

What each consumer states it needs is in §A2.3. The three sets do not intersect in a build that any one of them could take unchanged:

- `llvm-cc`'s purpose is the seed's bytes: `check.slop` runs the seed compiler and the new one on 13 inputs and `cmp`s (`:95-118`), and the second-stage test requires "every archive, the linked compiler and the three TableGen tools to be the first stage's bytes" (README `:56-58`). A PIC build, Zstandard, or another revision changes those bytes; the test then says so. So `llvm-build` is pinned to the seed's configuration by its own check, and `scripts/build-toolchain.sh:85-105` is that configuration's other copy.
- `rust-build` takes `llvm-config` and eleven archives at 22.1.8 from Rust's fork, PIC. rustc's bootstrap accepts "need >=21"; whether `rustc_llvm` 1.98.1 compiles against upstream `4bfd08c2` or `4154b56c` is not in the record, nor is the fork's difference from upstream (the fork's tree is in `build/rustc-port/llvm-source`, not compared here).
- `mojo-build` takes everything in `/opt/mojo-llvm` at Mojo's pin with MLIR, Clang's Basic library, Zstandard and the codegen patch; "Not tried: compiling Mojo against the seed's revision" (`:226`).

So "the largest common build" is one of two things, and the record does not say which is the owner's meaning: (i) three library packages, one per revision (`llvm-24-seed`, `llvm-22-rust`, `llvm-24-mojo`), each `FROM` a toolchain holding CMake and Python; or (ii) one package of the union (`clang;lld;mlir`, PIC, Zstandard, every patch) at one revision, which by the evidence above serves `llvm-cc` only if that revision and those flags equal the seed's (they do not: PIC and zstd are not the seed's), serves Mojo only if Mojo builds against it (not tried), and serves Rust only if the fork's revision is not needed (not tried). What (i) would change against today:

```text
DOLLY 7
TOOLCHAIN llvm-base                      # cmake-build with the Python LLVM's configure needs
FROM    /vX/demos/cmake/Dollyfile-cmake-build <sha>
INSTALL /vX/demos/python/Dollyfile-python <sha>
ENTRY /bin/foreground -i /bin/slop

DOLLY 7
PACKAGE rust-llvm                        # today's rust-llvm, as a package
REQUIRES HOST runtime@0
FROM    /vX/demos/llvm/Dollyfile-llvm-base <sha>
SOURCE  …/rust-llvm.tar.gz …; the two patches; FILE Dolly.cmake (today's :43-61); cmake; make -k -j4 …; the copies to /opt/rust-llvm
EXPORTS FOLDER rust-llvm /opt/rust-llvm
FILE    /opt/rust-llvm/LICENSE.TXT
```

- `rust-build` then says `INSTALL rust-llvm` in place of `COPY` (`:15`). Consequences read from the rules: a toolchain keeps installed files, and `rust-build:74` deletes `/opt/rust-llvm` after the second generation; whether a deleted installed folder is absent from the snapshot while its row stays in `/etc/dolly/installed` is the inventory's open question ("Whether a package keeps a `COPY` result its recipe later removes"), unanswered here. The five images `FROM rust-build` would carry the row in their record. `python`'s pin would then reach `rust-llvm`, `llvm-tablegen` and `mojo-llvm` through one base instead of three `INSTALL` rows; today it already "cascades to 30 of 97 images: the Rust, LLVM, Pi and 0 A.D. chains" (packages `:224-226`). `mojo-llvm` as a package is the same shape with its `FOLDER /opt/mojo-llvm`; `llvm-build` the same with `/usr/lib/llvm-build`, and `llvm-cc` would `FROM llvm-base` plus `INSTALL llvm-build` — but `llvm-cc` re-extracts the source tree for headers (`:28-31`), so the package would also have to keep the source headers it reads, or `llvm-cc` keeps its `SOURCE` row.
- **Simpler:** one base for the three (and `zero-ad-spidermonkey`, `meson`, which also install `python` as a build tool); the `Dolly.cmake` text and the staging functions (`stage_tree` in `demos/llvm/prepare-sources.sh:11-18`, `stage_mojo_tree` in `demos/mojo/prepare-sources.sh:3-10`, `tree()` in `prepare-rustc-sources.py:43-53`) are three copies that could be one site file each; the two patches are staged under three site paths with the same digests (`ec739fd5…` at `llvm/`, `rust/`, `mojo/`; `a9fb350e…` at `rust/`, `mojo/`), which `generate-routes.mjs` serves three times.
- **More complicated or lost:** nothing is built fewer times (three revisions remain three builds of 42, 28 and 65 minutes of `make`); a library package of 428-731 MB enters `amy list` beside `llvm-runtimes` ("in `amy list` and nobody installs it"); `rust-build`'s cleanup of its LLVM becomes a question of the record.
- **Who else could use it:** `zero-ad-spidermonkey` builds no LLVM; nothing else in the catalog compiles against LLVM. **What would rebuild:** every image on the Rust chain (24 by the root investigation's count), the LLVM chain (4), the Mojo chain (4), `zero-ad-spidermonkey` and `zero-ad-engine` if the base moves.
