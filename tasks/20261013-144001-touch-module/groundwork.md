# A touchscreen module in place of `buttons@0`: the groundwork

Read at `/home/daug/dev/dolly/work/rust` (branch `integrate/round-1013`, head `66f9fc47`, 2026-10-14; history shared with `main`, whose head is the same commit). Nothing was built or run; every number comes from `git`, `grep`, the files, the pinned sources in `.cache/` and the tasks. Line numbers are of this tree unless a commit is named. Quotes are marked as quotes. This report holds facts and the questions a design must answer; it proposes no contract.

## Summary (findings, no advice)

1. The owner asked three times for touch for programs: 2026-10-06 ("respond to touch, drag etc"), 2026-10-10 ("phone input … dragging zooming etc. Buttons is sort of irrelevant for that?"), 2026-10-13 ("if you touch with 2 fingers at the same time and do a zoom … the program should be able to recognize that"). What was built on 2026-10-10 (`7a6daada`, `c6fed63f`) answered a different sentence of the same request: "There should be no keyboard input, just a "button" menu and speech to text. API keys need to be pasteable."
2. Touch on the page has been decided three times, each way: 2026-08-31 a finger's drag scrolled the terminal and the page had a phone menu of buttons typing `/login openrouter` and `/model` (`aa0e63c0`); 2026-09-06 both were removed, "touch drags are ordinary pointer records … The host has no phone menu", a game drew its own touch buttons in Wasm (`6fe7dec1`); 2026-10-10 the drag-to-scroll came back and a pinch became Ctrl+= / Ctrl+- (`c6fed63f`, `077bb981`), both in page code, with "input@0's contract is unchanged" as the stated reason for adding no record type.
3. No contract carries a finger's identity today. `input@0`'s record has no pointer id (`host/input/input.h:84-97`); the page never writes `pointerId` or `isPrimary` into a record (`host/input/input.mjs:87-109`). A program holding the input lease receives every finger as the one pointer, button 0, with positions sampled once per animation frame, newest wins (`input.mjs:210-223`, `:141-152`).
4. Two sketches of touch exist in the record and neither was built: contact records inside `input@0` using the record's two reserved words for the id (`tasks/20261002-072000-input-host-module/TASK.md:208-213`, a seed round), and a module `touch@0` with its own ring, digest and boundary row (`tasks/20261005-222057-touch-input/TASK.md:26-35`). The owner's 2026-10-13 words choose "separate".
5. `buttons@0` is five things in one lease: a page-drawn strip (caption, 12 labels), `inputmode="none"` on the page's keyboard element while shown, the page's own Paste button and its clipboard read, operation 132 that types bytes into the terminal from inside Wasm, and the terminal area shrinking above the strip. Its lease has no foreground rule; `voice` holds it as a background job beside Pi (`demos/speech/Dollyfile-pi-phone:23-24`), which the input and display leases forbid (`host/input/kernel.c:193-194`).
6. Consumers in the tree that have a touch path of their own: SDL2 (`SDL_AddTouch`, `SDL_SendTouch`, `SDL_SendTouchMotion`, finger id, normalised x/y 0..1, pressure, and its own pinch/rotate gesture events), raylib (`CORE.Input.Touch`: up to 8 points with ids and pixel positions, a gesture library), Xonotic's engine (`SDL_FINGERDOWN` handling under `vid_touchscreen`), ClassiCube (`CC_BUILD_TOUCH`, not defined in Dolly's config) and 0 A.D. (`TouchInput.cpp`, compiled only for Android). Dolly's SDL2 driver and raylib adapter feed none of these today.
7. Coordinates of pointer records are pixels of the frame on the canvas (`input.mjs:352-357`): CSS size times device scale for the terminal (`src/ghostty/display.c:422-423`), the program's own logical size for a leaseholder. A leaseholder is given width, height, stride and format, not the scale or the CSS size (`host/display/display.h:102-108`).
8. The existing modules answered the same questions four ways: a kernel ring read under a lease that drops the newest and marks the loss (`input@0`); a page queue of 16 that drops the newest silently (`buttons@0`); a page queue of 96,000 frames that drops the oldest and counts (`microphone@0`); back-pressure with `EAGAIN` and no drop (`audio@0`). No module stamps a time on what it delivers; SDL and raylib stamp time themselves when they read.
9. Tests drive touch three ways today, all in `test/buttons-browser.mjs`: synthetic `PointerEvent`s with `pointerType: "touch"` and two ids (Chrome and Firefox), Playwright's Pixel 7 context with `page.touchscreen.tap`, and Chromium's `Input.dispatchTouchEvent` over CDP with one touch point. No test sends a touch to a program holding the input lease. The one real-phone session drove touch over CDP too; the "feel of drag and pinch" is listed as unverified.
10. Cost, measured on the newest modules: a module with a header and client changes the seed, so every image is rebuilt (buttons: 23 files, 15 outside its directory). Removing `buttons@0` also moves the seed; 21 files outside `host/buttons/` and `tasks/` name it. A page-only or kernel-only change rebuilds no image.

### 2.2 `input@0`'s pointer

**Record** (`host/input/input.h:84-97`, 128 bytes): `type, action, modifiers, flags, x, y` (u32/i32), `reserved[2]`, `key_length, code_length, text_length, reserved_length` (u16), `data[88]`. Types (`:13-25`): KEY 1, TEXT 2, FOCUS 4, PASTE 5, POINTER 6, SCROLL 7, POINTER_MOTION 8, POINTER_CAPTURE 9, POINTER_PRESENCE 10, DROPPED 11. POINTER: action RELEASE 0 / PRESS 1 / DRAG 2, modifiers, "button 0 to 4 in flags >> 8, x and y in canvas pixels" (`:75-76`). SCROLL: action is the unit (pixel 0, line 1, page 2), y in thousandths of the unit (`:77-78`). POINTER_MOTION: relative motion in thousandths of a CSS px, clamped at ±32,768,000 (`:79-80`). DROPPED: action is the count lost since the page loaded (`:83`). There is no id, no time, no pressure or size; `reserved[2]` is written as zero (`input.mjs:102-103`). The page's `writeRecord` takes `{type, action, modifiers, flags, x, y, key, code, text}` and nothing else (`:87`).

**Lease** (`input.h:120-133`; `kernel.c`): `dolly_input_acquire` (op 88) is ENOSYS where no page listens (`kernel.c:192`), EPERM unless the caller is the foreground or a descendant (`:193-194`), EBUSY while held (`:195`); `next_event` (op 89) takes one record or defers until a deadline (`:205-222`); `set_pointer_relative` (op 90) asks for pointer lock, which the page grants only on a trusted press on the canvas (`input.mjs:399-410`) and ends on Escape (`:317-321`); `release` (op 91). Exit or forced termination releases (`input_release`, `:262-264`); release drops every unread record, pointer and scroll included (`release_lease` → `discard_pending_input(0)`, `:179-187`). A foreground change without a lease drops unread keys but still hands pointer and scroll to the terminal (`:81-83`; `ring.h:22-26`).

**Ring** (`dolly-input-0.wat:6-23`; `input.mjs:80-129`): 256 records of 128 bytes in kernel memory; the page is the one producer. The last slot is kept for one loss mark, so 255 are usable (`:80-84`). A record that finds no slot is lost: counted in `data-input-dropped`, shown as "Input dropped: the program is not reading it", and one DROPPED record is written where the first lost record would have been (`:125-129`, `:498-502`). Pointer position and relative motion are samples: the newest position replaces an unsent one and is written once per animation frame while more than half the ring is free (`:138-162`); so a drag's path between frames is not delivered. Without a lease, the display's tick runs `dolly_input_ring_service`: POINTER and SCROLL go to the decoder (selection, scrollback), MOTION, CAPTURE, PRESENCE and DROPPED are discarded, the rest are compacted in order (`ring.c:28-58`). The page notifies the Worker for every record under a lease and for keys, text, paste and focus without one (`input.mjs:116-118`).

### 2.3 What the page does with a touch today (`host/input/input.mjs`)

| Event | No lease (the terminal) | Under an input lease |
| --- | --- | --- |
| `pointerdown`, `pointerType === "touch"` | Added to `fingers` by `pointerId`; the first finger becomes `touch` (the scroller); with two fingers `span` is their distance; `keyboard.focus()`; no pointer record (`:391-398`). A tap neither selects nor clears a selection. | The finger branch is skipped (`!transport.leased()` is false). `setPointerCapture`, `keyboard.blur()`, a POINTER PRESS with button `event.button` (0 for a finger) at frame pixels (`:411-416`). Every finger, any `pointerId`. If the program asked for relative motion, a trusted press requests pointer lock instead (`:399-410`). |

### 2.4 What the browser delivers, as the page uses it

The page listens to Pointer Events only (`pointerdown`, `pointermove`, `pointerup`, `pointercancel`, `pointerenter`, `pointerleave`, `:362-363`, `:389-460`); no `touchstart` listener exists. It reads `pointerType` (`:391`), `pointerId` (`:392-393`, `:411`, `:424`, `:442`, `:446`, `:454`), `clientX/clientY`, `button`, `buttons` (`:437`), `isTrusted` (`:402`), the four modifier keys. It reads none of: `isPrimary`, `pressure`, `width`, `height`, `tiltX/Y`, `twist`, `timeStamp`, `getCoalescedEvents()`, `getPredictedEvents()`. `pointercancel` is handled (the browser's way of saying a finger was taken by a gesture or lost). In the tests, Chrome's `Input.dispatchTouchEvent` reaches these listeners as pointer events (`test/buttons-browser.mjs:212-216`), and a `PointerEvent` constructed with `pointerType: "touch"` and `pointerId` 7 or 8 does in both browsers (`:122-129`, `:137-147`).

### 2.5 Coordinates

- A pointer record's `x, y` are "Positions are pixels of the frame the canvas shows" (`input.mjs:351-357`): `(clientX - bounds.left) * width / bounds.width` with `{width, height} = surfaceSize() ?? canvas`. `surfaceSize` is given only by the GPU module while its canvas is active (`host/modules.mjs:79`; `host/gpu/gpu.mjs:79`); otherwise the display canvas's backing size, which the presenter sets to the published frame's width and height (`host/display/display.mjs:236-239`).
- For the terminal the frame is the surface in CSS px times the device scale (`src/ghostty/display.c:416-423`: `width = css * scale_milli / 1000`), the surface being `mount.clientWidth/Height` and `devicePixelRatio` written by the page (`display.mjs:94-101`, `:256`), the scale clamped to 0.5–4. The decoder turns `x, y` into a cell by `padding` and `cell_width/height` in frame pixels (`display.c:769-781`).
- For a leaseholder the frame is its own logical size after `dolly_display_set_size` and "the page scales the frame to the canvas"; "It is not told when the page's surface changes" (`docs/display.md:78-80`). It receives `dolly_display_surface {generation, width, height, stride, pixel_format}` (`display.h:102-108`): no scale, no CSS size, no rotation.
- A finger's scroll record is in device pixels (`:431`: the CSS delta times `canvas.height / canvas.clientHeight`), which `handle_scroll` divides by `cell_height` (`display.c:843-849`). The pinch step is 20 CSS px (`:427`). Measured: Pixel 7 emulation 412x839 CSS at 2.625 (`phone-voice-pi:90`), the owner's phone 360x640 at 2x (`:197`).

## 5. The questions a designer has to answer

Each with the evidence that bears on it and the tension where there is one. No answer is chosen.

1. **What one touch is.** The owner: identity lasting from start to end, position, phase, so a program can tell a tap from a drag and two fingers apart as a zoom (`TASK.md:27-34`). The two sketches: id, down/move/up/cancel, position "in surface pixels", pressure and radius "where the browser reports them" (`touch-input:26-30`). The browser gives `pointerId`, `isPrimary`, `clientX/Y`, `pressure`, `width`, `height`, `timeStamp`, coalesced events, `pointercancel`; the page uses the first three and the cancel (2.4). SDL wants a pressure 0..1 and stamps its own time (3.1); raylib wants ids and pixel positions and stamps its own time (3.2); the existing records carry no time (4). The input record has two unused words (`input.h:91`) that the 2026-10-06 sketch meant for an id; the owner's 2026-10-13 word is "separate".
2. **Touches and the single pointer, both or instead.** Today a finger under an input lease is the pointer with button 0 (2.3); SDL synthesises a mouse from the first finger itself when a touch device exists (`SDL_touch.c:252-300`); the `gamedev-phone` program of 2026-09-06 lived on pointer records alone (1.1). A program holding both leases would get a finger twice unless one side stops; `c6fed63f` kept the pointer path on purpose ("still reads touch as its pointer").
3. **Who gets a touch when no program holds the module.** Today the page itself turns one finger into terminal scroll and two into font keys (`input.mjs:374-436`), against the contract's "what a record means is decided in Wasm" (`dolly-input-0.wat:3-4`); the 2026-10-06 sketch put "the decoder's mapping to scroll and selection" in Wasm (`input-host-module:210-212`); the 2026-09-06 decision was that the browser turns no touch into a scroll (1.1). The terminal's scroll and pinch exist because Pi on a phone needed them (`870b6ab4`, "Pinch to zoom was promised for the terminal", `phone-voice-pi:157`).
4. **What the page must do so the browser does not pan or zoom.** `touch-action: none` is on the canvas and the strip (`terminal.html:37`, `:92`); the indicators still pan (`phone-voice-pi:107-108`); a drag on them "cannot pull the page to reload" was the reason for `9be231ea`. Whether a hold changes this is nowhere recorded.
5. **One holder or several, and which processes.** `input@0` and `display@0`: one, the foreground or a descendant (`kernel.c:193-195`); `buttons@0`, `microphone@0`: one, any process (`device-lease.c:35-45`), which is what lets `voice` hold it as Pi's background sibling (`Dollyfile-pi-phone:23-24`). A touch module held by a foreground rule could not be held by a program like `voice`; one without it is open to a background process, as `buttons@0` is.
6. **A ring or a call, and what a full queue does.** Four answers in the tree (4): drop newest and mark (`input@0`), drop newest silently (`buttons@0`), drop oldest and count (`microphone@0`), refuse with `EAGAIN` (`audio@0`). The input ring samples the pointer once per frame and never loses it (`input.mjs:138-162`), which loses a finger's path between frames; the task wants a drawing program ("draw with several fingers", `touch-input:37-38`). Phones send moves at the screen's rate per finger; nothing here measured the rate.
7. **In which coordinates.** Pointer records are frame pixels (2.5); SDL normalises by the window (3.1); raylib wants screen pixels (3.2); the sketch said "surface pixels"; a leaseholder is not told the scale or the CSS size (`display.h:102-108`), and a program at the terminal has no frame of its own. Whether a touch position refers to the canvas, the frame, or the terminal's cells is open.
8. **What a program that draws on the terminal sees.** A program without a display lease (like `voice`) has no frame; the terminal's cells are the display plugin's (`src/ghostty/display.c`), not published to programs beyond `TIOCGWINSZ`; a tap on the terminal today raises nothing in Wasm (2.3). The first task version's three places (1.5) are the recorded options; no code exists for any.
9. **What replaces the strip for `voice` and `pi-phone`, and where the Paste button's clipboard authority goes.** As a consequence only: without `buttons@0`, (a)–(e) of 2.1 have no home. The clipboard reaches a program today only by the browser's own paste event into the keyboard element (`input.mjs:480-486`) or the page's Paste button (`buttons.mjs:41-44`); the boundary says "Nothing is read from the clipboard but a paste the user makes" (`docs/browser-boundary.md:205`). The on-screen keyboard is kept down only by `inputmode="none"` while the strip shows (`buttons.mjs:30`); a tap on the terminal calls `keyboard.focus()` (`input.mjs:395`). Typing into another program's terminal is operation 132 (`host/input/kernel.c:134-163`); `pty@0` exists since `d9f8104e`/`706afa45` and was named as a possible home (`e330d782`).
10. **A mouse on a desktop.** SDL has `SDL_HINT_MOUSE_TOUCH_EVENTS` (`SDL_hints.h:1689`); raylib's gestures can be "simulated from mouse inputs" (`rcore_memory.c:22`); 0 A.D. has `EMULATE_FINGERS_WITH_MOUSE` (`TouchInput.cpp:63`). The page today sends a mouse only as the pointer. Whether the module says anything to a desktop, or the tests must emulate (11), is open.
11. **How a test drives it.** Three ways exist (`test/buttons-browser.mjs`): dispatched `PointerEvent`s with `pointerType: "touch"` and distinct ids, which run in Chrome and Firefox (`:122-147`); Playwright's `devices["Pixel 7"]` context with `page.touchscreen.tap` (`:162-173`); CDP `Input.dispatchTouchEvent` with a `touchPoints` list, one point used, Chromium only (`:212-216`). The 2026-10-06 task asked for "emulated multi-touch in Chrome and Firefox (Playwright touch contexts)"; the phone part of the buttons test runs for Chromium only (`:149`). No test sends a touch to a leaseholder (grep: none).
12. **Limits and what is counted.** `AGENTS.md`: "Count every new resource kind … in its quotas"; `input@0` counts records (256 of 128 bytes) and the paste buffer; `buttons@0` counts events (16); `microphone@0` frames (96,000). A touch module's countable things in the evidence: fingers at once (raylib 8, ClassiCube `INPUT_MAX_POINTERS`, browsers' own limits unmeasured), records in a ring, moves per frame, bytes per record.
13. **Whether it has an import or a mailbox.** `input@0` and `display@0` are mailboxes with no import (`module.json`, `imports: []`); `buttons@0`, `microphone@0`, `gpu@0`, `audio@0`, `nena@0` are imports; the boundary's rule is that a new import or mailbox is reviewed in `abi/dolly-browser-0.wat` and the review map (`host/README.md:59-62`; `docs/browser-boundary.md:253-254`).
14. **What the page shows while a program holds it, and whether `nena` may switch it.** `microphone@0` and `gpu@0` show indicators; `input@0` and `display@0` show nothing; `input@0` and `display@0` are `fixed`, `buttons@0` is switched (4). A touch module that the terminal also uses (3) would face `input@0`'s reason for `fixed`: "it is the terminal's input" (`host/input/module.json:5`).
15. **What it costs to add and what removing `buttons@0` rebuilds.** Measured (`module-sdks` §2.7): a new module with a header and client moves `dolly.data`, so every image is rebuilt (buttons 23 files: 8 inside, 15 outside; microphone 32; nena 57); the two review points and `host/manifests.mjs` are touched by every module; `Dollyfile-dolly-docs` and its three dependents by every contract commit. Removing `buttons@0` removes a header and an archive from the seed (every image again) and touches the 21 files that name it outside its directory: `AGENTS.md`, `Dollyfile-dolly-docs`, `abi/README.md`, `abi/dolly-browser-0.wat`, the three speech recipes, `demos/speech/README.md`, `speech-browser.mjs`, `voice.c`, `docs/browser-boundary.md`, `docs/input.md`, `host/manifests.mjs`, `src/device-lease.h`, `src/process-kernel.h`, `terminal.html`, four tests and a fixture; and, if operation 132 goes, the typed queue in `host/input/kernel.c` and `src/dolly.c:65-78`. Page-only and kernel-only changes rebuild nothing (`module-sdks` §2.6).
16. **A demo and a phone.** The task wants "a small program proves it (two fingers zoom something it draws), in Chromium with touch emulation and on a phone"; the 2026-10-06 task wanted a `touch-demo` APPLICATION with the contact state visible (`touch-input:37-39`); every APPLICATION must declare `display@0` (`scripts/lint-dollyfiles.mjs:67-68`); a graphics image has never been opened on a phone (`touch-input:17-18`).
