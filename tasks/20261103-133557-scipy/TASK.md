## OpenBLAS (the `openblas` package)

`demos/python/Dollyfile-openblas`: OpenBLAS 0.3.34's release archive, built by its CMake project
with `-DARCH=wasm -DBINARY=64 -DTARGET=WASM128_GENERIC -DCMAKE_C_FLAGS=-msimd128 -DNOFORTRAN=1
-DC_LAPACK=1 -DNO_LAPACKE=1 -DUSE_THREAD=0`, static; `pkg-config openblas` gives
`-I/usr/include/openblas` and `-lopenblas`.

Decisions, each measured in a session (`build/scipy-evidence/explore.mjs`, `explore3.mjs`,
commands and outputs beside them):

- No claim of Emscripten. OpenBLAS detects wasm only under `__EMSCRIPTEN__` (`ctest.c`, which then
  also prints `OS_WINDOWS`). Its CMake project takes the architecture as configuration: `ARCH` is
  a cache variable that `cmake/system_check.cmake` only defaults (it warns "Target ARCH could not
  be determined, got wasm64"), `BINARY` too (it would default to 32).
- SIMD128 kernels, not the generic C ones. The task assumed SIMD128 needed a change to Dolly's
  target; `cc` has taken `-msimd128` per unit since `69552b325` (2026-10-07, "every browser with
  memory64 has it"), as Clang does, so upstream's own wasm target `WASM128_GENERIC` builds with no
  change to the compiler. Measured against `TARGET=GENERIC` (which also needed `kernel/CMakeLists`
  to read `KERNEL.generic` only if it exists, and `param.h` to give GENERIC on wasm a cache
  blocking): DGEMM 1000 x 1000 0.090 s against 0.19 s (22.3 against 10.4 GFLOP/s), DGESV 1000
  0.031 s against 0.065 s, Chromium; both pass utest and utest_ext.
- CMake, not the Makefiles: the Makefile build needs `ctest.c` patched (no `ARCH_WASM` without
  Emscripten) and archives with `ar -ru`, which Dolly's `ar` refuses (`only deterministic archive
  updates with r, q or s`; GNU and LLVM `ar` accept `u` and ignore it in deterministic mode).
  `c_check` also runs `cc -S`, which Dolly's `cc` does not take. CMake archives with Dolly's
  platform rule (`ar rcs`).
- `openblas-dolly.patch` (proposed upstream, not filed; its head says why): LAPACK's subroutines
  return void. 779 lines of 190 files, generated by one rule: OpenBLAS defines the LAPACK routines
  it implements (`getrf`, `getrs`, `gesv`, `potrf`, `lauum`, `trtri`, `laswp`, `laed3` and their
  unblocked forms), 42 files of its C translation (`larft`, `larf1f`, `gedmd`, `geqp3rk`...) and
  INSTALL's `ilaver` as returning `int`, and declares some of them `int` and others `void` where
  it calls them; SciPy declares every subroutine `void`. WebAssembly checks a call's type, and
  wasm-ld links a mismatched call to a trap: before the patch OpenBLAS's own `utest` trapped at
  `potrf:bug_695`, a check program's `dgesv_` trapped, and linking every object of the library
  into one DSO warned of 108 mismatched symbols (`dgeqrf_` calls `dlarft_` as void). After it: no
  mismatch, `utest` 124 of 124 and `utest_ext` 1535 of 1535 pass. (`xerbla_` stays `int`, as its
  1035 declarations say; the 3.12 routines also called it without its length.)
- `NO_LAPACKE`: nothing in Dolly uses LAPACK's C interface; SciPy declares its own prototypes.
- Size: `libopenblas.a` 11.6 MB; the package's snapshot 11.8 MB, its packs 3.2 MB compressed.
  Built in 2.5 min in a session (`-j8`), 367 s as an image in a `bigbuild` slot.
- Tested by python-data's demo test: a session of `cc`, `pkgconf` and `openblas` links
  `openblas-check.c` through `pkg-config openblas` and runs it (a product, a solve, a Cholesky and
  a QR of known results, the QR through `dlarft_`, which trapped before): Chromium 10.6 s (DGEMM
  500 x 500 at 19.9 GFLOP/s), Firefox 11.6 s (15.2 GFLOP/s). `amy-browser.mjs` names the demo as
  where the package is used.

Against NumPy's own fallback (python-data's NumPy has no BLAS), in a session, Chromium, the same
arrays through `numpy` and through SciPy's OpenBLAS (`scipy.linalg.blas.dgemm`,
`scipy.linalg.solve`):

NumPy built on the package would take its products and solves too (`-Dblas=openblas

## SciPy 1.18.1 (explored in a session, `build/scipy-evidence/explore2.mjs`, `explore4.mjs`)

A session of `system`, `python`, `meson`, `pkgconf`, `cmake` and python-data-build's NumPy root
(`COPY`), with this branch's OpenBLAS built in it, builds SciPy's sdist with pip as
python-data-build builds the others (`--no-build-isolation`, meson-python's release build,
`-D_without-fortran=true`, `-Duse-pythran=false`): 1144 Ninja steps in 13 min 17 s at Ninja's
default jobs (5 min with `-j8`), a 21.0 MB wheel; the root is 93.8 MB in 1420 files (tests
17.1 MB, 102 extension modules 63.3 MB), 21.3 MB as a tar.gz at level 6, what it would add to
python-data's packs. What it took, in the order met:

1. `c_std=c17` (SciPy's `project()`): Meson grants Clang C17 from version 6 and reads no version
   from Dolly's `cc --version`. Fixed on `demo/pydata-seed` (`src/commands/cc.c`, a seed input,
   built there, awaiting a round). Emulated in the session by a `cc` wrapper.
2. `-pthread` with `-shared`: `scipy.fft`'s duccfft, `scipy.optimize`'s HiGHS and `scipy.stats`'
   `_qmc_cy` take Meson's `dependency('threads')`, which Meson gives every POSIX compiler as
   `-pthread`, and Dolly's compiler refuses it for a DSO ("-pthread requires a static process").
   Matplotlib 3.11's HarfBuzz met the same. A proposal (below); emulated by the wrapper dropping
   `-pthread` from `-shared` links.
3. `__small_fprintf` (`scipy.optimize._trlib`): LLVM's printf rewrite, which a `-rdynamic` host
   does not export. Fixed on `demo/pydata-seed`; emulated by `-fno-builtin`.
4. Two SciPy declarations wasm-ld links to traps ([`scipy-dolly.patch`](scipy-dolly.patch), kept
   here until SciPy has a recipe; proposed upstream, not filed): `_common_array_utils.hh`
   declares `?getrf` and `?getri` returning `CBLAS_INT`, while SciPy's other declarations and
   LAPACK make them subroutines (`scipy.linalg.inv` and `det` trapped); trlib passes `dlagtm` a
   hidden string length that no other SciPy call passes and OpenBLAS's C LAPACK does not take. The
   link log's 12 mismatches are then 3, all `cython_lapack` exports SciPy itself never calls:
   `ilaver` (OpenBLAS's `int`, void since `bd7329ca4`), `xerbla_array` and `chla_transtype` (a
   hidden length, a CHARACTER result).
5. A weak `_ZTH` (HiGHS's `thread_local`) failed `import scipy.optimize` with "undefined symbol":
   fixed in the DSO loader (`5548dbdd8`).
6. `import scipy.optimize` (and `stats`, `integrate`, `interpolate`, `signal`) then stops
   CPython: `_uarray`'s `thread_local` maps have destructors, so libc++abi registers them with
   `pthread_key_create(key, destructor)`, and the thread stubs Dolly's CPython is built with
   (`Python/thread_pthread_stubs.h`) call `Py_FatalError` for any destructor. Fixed in
   `cpython-dolly.patch`: the stubs serve one thread, which exits with the process, and POSIX runs
   no key destructor then, so there is none to keep. The python recipe's new check (a C++ library
   whose `thread_local std::string` ctypes loads) stopped Python before, in a session of the old
   python-data ("pthread_key_create destructor is not supported", status 134). Real threads
   ([pythreads](../20261103-134653-pythreads/TASK.md)) replace the stubs and keep the check.

With items 1 to 3 emulated and 4 to 6 fixed, in Chromium (python rebuilt with the stub fix):

## Proposals (the owner's)

- **`cc -shared -pthread` links as `cc -shared`** (`src/compiler.cpp`, the seed compiler: an
  `llvm-cc` round). A DSO has no thread runtime of its own: it shares its host's libc, and every
  DSO host is a single-thread process (threads@0 has no DSOs), whose `pthread_create` fails with
  `EAGAIN`. So `-pthread` adds nothing to a DSO, as `-lpthread` adds nothing to any link; the
  objects compile alike with and without it (atomics and bulk memory are always on). Meson gives
  `-pthread` to every `dependency('threads')`, required or not: SciPy (fft, HiGHS, qmc) and
  Matplotlib 3.11 (HarfBuzz) cannot link a module without it. The diff:
  ```diff
  -  if (options.pthread && (options.shared_library || options.kernel_plugin || options.export_dynamic)) {
  -    std::fputs("dolly-cc: -pthread requires a static process; shared libraries and -rdynamic are unsupported\n", stderr);
  +  // A DSO takes its host's libc and threads: -pthread adds nothing to it, as -lpthread.
  +  if (options.shared_library && !options.kernel_plugin) options.pthread = false;
  +  if (options.pthread && (options.kernel_plugin || options.export_dynamic)) {
  +    std::fputs("dolly-cc: -pthread requires a static process; -rdynamic is unsupported\n", stderr);
  ```
  With it (emulated) SciPy builds. Not measured: whether HiGHS's thread pool fails cleanly when
  `pthread_create` refuses, since `import scipy.optimize` stops at the next proposal first.

## Found, not acted on (the compiler's, each an `llvm-cc` round)

- Dolly's `ar` refuses the `u` modifier (`ar -ru`, OpenBLAS's Makefiles); GNU and LLVM `ar`
  accept it and ignore it in deterministic mode.
- `cc` refuses `-S`, `-dumpversion` (OpenBLAS's `c_check` and `Makefile.system` probe with them)
  and `-fno-builtin-NAME` (Clang takes it per function); `-fno-builtin` alone is accepted.

## Lessons

- WebAssembly checks every call's type, and native ABIs forgive what it does not: an `int`
  definition called as `void`, a hidden string length nobody reads. OpenBLAS's C LAPACK and SciPy
  each carried such mismatches that no native platform shows, and wasm-ld turns each into a trap
  with only a warning. Linking every object of a library into one throwaway DSO prints the whole
  list at once (108 symbols for OpenBLAS); a package's check should do that, not wait for a caller
  to trap.
- Check a premise against the code before building around it: the brief (and the task) said
  SIMD128 would need a change to Dolly's target, but `cc` has taken `-msimd128` per unit since
  2026-10-07 (`69552b325`), so OpenBLAS's own wasm kernels were one flag away and twice as fast.
- A chain of blockers shows one link per build. SciPy met six (Meson's C17, `-pthread` in a DSO,
  `__small_fprintf`, two of its own declarations, a weak GOT entry, CPython's key destructor); a
  session in which a wrapper emulated each known fix walked the chain in an hour, where image
  builds, each waiting for a slot, would have shown the first.
- The browser broker caps uploads, so a session cannot post a 10 MB library back: inspect a
  binary inside the session (a 40-line Python reader of the import and dylink sections found the
  GOT entry's missing weak flag).
- An edited recipe stops every new session of the checkout server ("stale recipe pin", "recipe
  changed") until its image is rebuilt, which the shared build slots made a half-hour wait. Boot
  the sessions an experiment needs before editing the recipes they serve, or keep the edit for
  after.
- The browser tests rebuild the loader's bundle from source before each run: a "before" run with
  the new test and the old `dist` bundle used the fixed source and passed. To see a test fail,
  revert the source.
