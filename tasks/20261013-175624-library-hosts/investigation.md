# Part B: what a library package declares of host modules

**Summary (findings, no advice)**

1. The sentence "a library or compiler those every program built with it needs" entered `docs/dollyfile.md` with `8bfcd884` (2026-10-05), the commit that made `sdl2` the first library package with a stamping client; `git log -S` finds no earlier form. The rule it extends, "A package declares the modules its programs need, and `INSTALL` checks that the installing recipe declares them too", is Phase 3's (`9fc8b997`/`5ec4783c`, 10-01) and is marked "(Owner correction.)" only for "Host requirements are explicit and never inherited" (`tasks/20261001-214000-dollyfile-v6/TASK.md:217-231`). `b6bd8842` (10-06) added `input@0` to the example; `403d3abb` (10-06) `runtime@0`.
2. The owner's one ruling on a module a library could carry is on sockets (2026-10-08): "declared only by programs that require only at link time. Things that don't need it to run shouldnt require it." `libevent` follows it: it declares none and says "A program that gives it sockets links -ldolly-sockets too" (`demos/tmux/Dollyfile-libevent:7`).
3. Mechanically a `REQUIRES HOST` line on a library package does three things: it is checked against the installer's declared set (or `/etc/dolly/enabled` under `nena@0`) at the `INSTALL` row (`src/dollyfile.c:1109-1113`) and by the page's graph (`src/dollyfile-graph.mjs:62-66`); it is written into the package's receipt (`:1029-1033`); and at the package's own sealing its retained executables are checked against it (`:2108-2120`). It never reaches a consumer's manifest, and no archive is scanned: sealing opens only files that begin with `\0asm` (`:2025`), and an `.a` begins with `!<arch>`.
4. What stamps a program is the client member the link pulls in (`include/dolly/host.h:10-14`; "Static archives contribute only referenced members, so an executable still records only the host modules it calls", `790d66ec`). A library's archive stamps nothing itself; it causes a stamp when its code references a client, because `cc` links every client archive by default except sockets and pty (`src/compiler.cpp:811-823`, module-sdks §175).
5. At launch the loader reads the executable's `dolly.host` records (`host/requirements.mjs:26-51`) and refuses one the image does not declare or `nena` has not enabled (`:55-62`; `src/process-supervisor.mjs:346-347, 416`): "not declared by this image (REQUIRES HOST)" or "is not enabled: nena enable x".
6. Of 22 library-shaped packages counted, 12 declare nothing beyond `runtime@0` and reference no client (both readings agree); `sdl2`, `raylib`, `curl`, `janis` declare exactly what their code references (both readings agree); `openal`, `libevent`, `libuv`, `lua` declare none and have an optional path a program may give them (the readings differ); `mojo` declares none and ships `libmojo-gpu.a`, which references `gpu@0` (the readings differ, and the recipe says so: `demos/mojo/Dollyfile-mojo:18-19`); `rust` and `python` declare their own programs' modules, and the four Rust packages built with `rust` each declare `http@0` and `threads@0`.
7. The two readings give different results where a library has a backend a program may or may not use: a llama.cpp package with `gpu@0` cannot be installed by `speech-build`, `speech-to-text-mic` or `pi-phone`; without it a program linked with `ggml-webgpu` is refused at start unless its image declares or enables `gpu@0` (engines A4(a)).
8. The 2026-10-12 packages task read `openal` the other way ("its programs need `audio@0`, which no image people install into declares", `:104`); `edef36bc` (10-13) made it with none, and `default` installs it (`test/amy-browser.mjs:222-229`). Both readings are in the record one day apart.
9. `nena@0` (`a182787a`, 10-13) changed what a refusal costs where the image declares it: `default` does (`Dollyfile:9`), so a refusal at `amy install` and at a program's start names the command, and the session can enable the module and go on. Every application and toolchain declares `http@0` (the 62 recipes without it are all packages), so `curl`'s `http@0` refuses nothing today.
10. Not findable here: whether `libdisplay.so` carries a `dolly.host` record (no built file on disk; the `display` package declares `display@0` and the doc says it "asks only for the first"); whether a `-pthread` ggml stamps `threads@0` on `dolly-llama`; whether the 10-05 sentence was the owner's; what "every program built with it needs" means for a library with an optional backend.

## B2. What is checked today

### B2.1 At sealing

`seal_manifest` (`src/dollyfile.c:2108-2120`) walks `engine->keep`, skips anything but a regular file (`:2113`), and calls `check_executable_hosts` (`:2020-2049`), which reads eight bytes and proceeds only when they are `\0asm\1\0\0\0` (`:2025`); for such a file it walks the sections and, in a custom section named `dolly.host` (`:2033-2043`), checks each 72-byte record's `name@version` against `host_declared` (`check_host_section`, `:1999-2017`): "PATH uses X: add REQUIRES HOST X" (`:2012`). A stamp is what `DOLLY_HOST_REQUIRE(name, revision, digest)` emits: a record in the custom section `dolly.host` of the object it is compiled into (`include/dolly/host.h:10-14`); each client has one (`host/*/client.c`, 14 files; `host/dso/client.c:18`). An archive file begins with `!<arch>`, so a retained `.a` is opened, fails the magic test and is skipped; its members' records are not read. A `.so` (`libdisplay.so`, `lpeg.so`, `luv.so`) is a Wasm module and is scanned. So a library package that retains only archives and headers seals with any host list, including none; the doc states the same ("An archive stamps nothing", the task's filing).

### B2.2 At `INSTALL`

- In a build: `read_artifact_receipt(install=1)` reads the package's host list from its receipt and refuses a module the installing recipe does not declare (`:1105-1116`), before any file changes (`:1395` comes after). The page's graph refuses the same statically for the direct target (`src/dollyfile-graph.mjs:62-66`: "X needs REQUIRES HOST …"), which the lint and `/view/` run. A package's own rows were checked the same way when the package was built, so a package's list covers its rows' lists.
- In a session: `install_live` reads `/etc/dolly/enabled` when the image declares `nena@0` (`:2207-2214`); `host_enabled` (`:1063-1069`) counts beside `host_declared`; the refusal is "needs X: nena enable x" (`:1111`) or "needs X: add REQUIRES HOST X" (`:1112`). `amy` runs the engine before fetching any row's snapshot, so a refused package installs nothing (`amy.c:264-281`; `package-dependencies:92-94`).

### B2.3 At launch

`process-supervisor.mjs:343-348`: the executable's `dolly.host` records are read (`executableHostRequirements`, `host/requirements.mjs:26-51`) and checked against the host's available set (`checkHostAbi`, `:55-62`): "host module X is not enabled: nena enable x" when `nena@0` is available, else "host module X is not declared by this image (REQUIRES HOST)"; a different digest: "has a different layout than this program was built for". The check runs again at every launch (`:416`, "disabled a module since"), as `a182787a` says.

### B2.4 So, mechanically, a library package's `REQUIRES HOST` line

| Who | What the line does |
| --- | --- |
| (i) a build image that installs it | must declare the module too, or the row fails at `:1112` and the graph at `dollyfile-graph.mjs:65`; the module is then in that image's manifest and the page enables it at boot; nothing is stamped by the install |
| (ii) an application that installs it | the same; the application's own retained programs are checked at its sealing for what they stamp, independent of the line |
| (iii) a session that `amy install`s it | refused by name unless the image declares the module or `nena` enabled it (`:1109-1113`); nothing is fetched for the rows on refusal |
| (iv) a program later linked against it in a session | the line plays no part; the program is stamped by the client members its link pulls in (because the library's code references them, or the program's does); at launch the loader checks those stamps against the image's declared set plus what `nena` enabled |

## B4. Where the two readings give different results

### B4.1 A llama.cpp/ggml library package and the speech images (engines A4(a))

`llama-build` builds the six archives with no `gpu@0` (`:3-8`) and seals; `ggml-webgpu` references `dolly/gpu.h` and `dolly-llama` links `-ldolly-gpu` (`local-llm-build:27`). Under reading (b) as `sdl2` is read, a `llama-cpp` package declares `gpu@0`: `speech-build` (hosts `runtime display input download buttons http microphone threads upload`), `speech-to-text-mic` and `pi-phone` (no `gpu@0`) cannot `INSTALL` it (refused at the row by name, `:1112`; by the graph before a build starts); a session on `default` is refused at `amy install` with "needs gpu@0: nena enable gpu" and installs nothing; after `nena enable gpu` the same command installs. Under reading (a), the package declares `runtime@0`; any image installs it; a program linked with `-lggml-webgpu` is stamped `gpu@0` at link and refused at its start in an image without it ("not enabled: nena enable gpu" on `default`; "not declared by this image" elsewhere); a program linked with `ggml-cpu` alone is not stamped and runs anywhere. What the recipe states: under (b) the module and nothing of the CPU half; under (a) nothing of the GPU half, unless a comment (as `mojo`'s). Two flag sets and two ggml revisions stand before either (A4(a)).

### B4.2 `openal` in `default`

Today: `runtime@0`, installs into `default`, and the amy check "compiles a C++ program that plays a square wave from a buffer and finds it in the rendered samples" with no audio module (`more-packages:154-156`; `test/amy-browser.mjs:222-229`). Under the 10-12 reading (`audio@0`): `default` lacks it, so `amy install openal` is refused "needs audio@0: nena enable audio"; `zero-ad-deps` (declares `audio@0`, `:4`) could install it. In both readings a player that links `-ldolly-audio` is stamped `audio@0` and, on `default`, is told at its start "nena enable audio". So the difference is when the session is told: at install (b) or at the program's start (a), and whether a program that renders to a buffer and never plays may use the library on `default` at all.

### B4.3 `mojo` in `default` against `mojo-gpu`

`mojo` declares `runtime@0` and installs `cc`; `mojo-gpu` is `FROM system`, `INSTALL mojo`, and declares `gpu@0` (`demos/mojo/Dollyfile-mojo-gpu:7, 14-15`: "A shell with the Mojo compiler … in an image with a GPU: kernels run here"; `:31` "The compiler and the link work here; a kernel runs where there is a GPU"). On `default`: `amy install mojo` installs; `mojo build` of a kernel program links `-lmojo-gpu -ldolly-gpu` (`modular.cfg`) and the executable is stamped `gpu@0`; its start is refused "host module gpu@0 is not enabled: nena enable gpu"; a program without a kernel runs. Under reading (b) `mojo` would declare `gpu@0`: `default` refuses the compiler by name, including for programs with no kernel, until `nena enable gpu`. The recipe states the choice in words (`:18-19`); the manifest states `runtime@0`.

### B4.4 `curl`

`curl` declares `http@0` and both readings agree (`libcurl.a` references the http client). A session without `http@0` does not exist in the catalog: every application and toolchain declares it (the 62 recipes without it are all packages), `nena` never switches it (`a182787a`), and `amy` itself needs it for the index (`amy.c:25`; `Dollyfile-amy` declares `http@0`, `packages@0`). So the line refuses nothing today; it would refuse an embedding's image that lacked `http@0`, which is the case the line exists for.

### B4.5 A library with an optional backend

In the tree: `openal` (no playback backend; a player adds `audio@0`), `libevent` (sockets by `-ldolly-sockets`), `libuv` (sockets through libc's refusals), `sqlite` (no loadable extensions: "a program loads none without -rdynamic and dso@0", `Dollyfile-sqlite:10`), `lua` (`dso@0` with `-rdynamic`). All five declare nothing for the optional path, and the ones that say why say it in a comment (`libevent:7`, `sqlite:9-10`, `mojo:18-19`). The owner's sockets rule is the recorded reason for one of them. Under reading (b) each would declare the backend's module for every program built with it; `tmux-panes` declares `sockets@0` because `tmux` does, which is reading (b) applied by the program's package, not the library's.

### B4.6 What `nena enable` changes, counted

With `nena@0` declared (`default` and the `nena` package alone, by the recipes), a refusal at `INSTALL` (`:1111`) and at launch (`requirements.mjs:58`) names `nena enable NAME`; the Worker records the enabled set in `/etc/dolly/enabled`, which a loaded session has again before its `ENTRY` (`a182787a`). So on `default` reading (b) costs one command before the install and reading (a) one command before the first start; on an image without `nena@0` (every other application: 19) reading (b) refuses the package for good and reading (a) refuses the program for good. An embedding's `DOLLY_HOST_MODULES` bounds what `nena` enables (`a182787a`), which neither reading changes.
