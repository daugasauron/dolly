# The recipe language parsed twice, by the engine and by the page: the investigation

Read on `work/rust` (`integrate/round-1013`, head `1d1f6663`, 2026-10-14); history shared with `main`; the reflection's tree is `d89bca74`. Nothing was built or run; every number comes from `git`, `grep`, `awk` over the files and the generated registry `dist/dolly-images.mjs` present in the tree. Line numbers are of this tree unless a commit is named. The sibling investigations [`dollyfile-words`](../20261013-144241-dollyfile-words/investigation.md) (§2, "Who reads the names") and [`roles`](../20261013-144241-roles/investigation.md) (§2.2–2.3) already describe what the page's parser and graph read of `REQUIRES`/`EXPORTS`/`FILE`/`FOLDER` and of the role line; this report cites them and does not repeat them.

## Summary (findings, no advice)

1. The JavaScript parser is as old as the language. `src/dollyfile-view.mjs` was created in the same commit as `src/dollyfile.c` (`9e013dd9`, 2026-08-31), for Node (the route registry) and a source viewer. That day's document said: "The authoritative parser and executor is the C program … The browser does not parse or execute build rows. JavaScript only discovers image names for routes and renders source text for the viewer." The page itself first imported the parser with DOLLY 3 (`99093739`, 2026-09-06), the commit that made images "complete image artifacts" the page has to supply before the engine runs.
2. The reason the page knows the closure before the kernel runs is mechanical and is in the code: a `FROM` base is restored as the kernel's filesystem before `/bin/dollyfile` is spawned, and the engine binary is inside that base (`src/runtime-worker.mjs:187-200`; `docs/dollyfile.md:136` "The build runs the base's `/bin/dollyfile`"); every `INSTALL`/`COPY` snapshot is a file the Worker writes before the spawn (`:172-175`); builders run "without local services" (`docs/browser-boundary.md:135-139`). In a build, `ROW_FIRST` (3) is a failure, not a request (`src/dollyfile.c:1654`, `runtime-worker.mjs:268`). Only `amy` treats 3 as a request, and its fetch goes to `packages@0`, which serves a pin only if the registry, written by the JavaScript parser in Node, lists it as a package (`host/packages/service.mjs:32`).
3. The host list the page trusts is the JavaScript parser's output in every path: the registry (`scripts/image-definitions.mjs:153`), the packaged metadata file (`scripts/build-system-snapshot.mjs:159`, cross-checked against the registry at `src/image-artifact.mjs:54`), and the "sealed artifact" of a rebuilt or custom image, whose `hostRequirements` field is computed by the JavaScript graph over the recipes retained inside the snapshot (`src/image-artifact.mjs:184-191`). The engine seals its own host list into the binary receipt `/etc/dolly/artifact` (`src/dollyfile.c:1030-1033`); no JavaScript reads that list (`image-artifact.mjs:182` checks only that the file exists).
4. Under the threat model, every trust input is anchored in a hash the page holds: the root recipe inside a sealed snapshot must hash to the page's `recipeSha256` (`image-artifact.mjs:181`), each chain recipe to the pin in its parent (`src/dollyfile-graph.mjs:32`), catalog recipes to the registry (`image-artifact.mjs:23-34`), packs to the metadata (`:165,173`). A compromised build cannot change the module set the page derives without breaking SHA-256. It can choose the `ENTRY` the page runs (`/etc/dolly/entry`, `runtime-worker.mjs:59`), which is authority it already has.
5. Parity is tested, not assumed: 232 cases (191 literal, 41 by spread) run through both parsers (`test/dollyfile-parser.test.mjs:44-53`), the C side as a native build of the real `dollyfile.c` with four stubs (`test/fixtures/dollyfile-parser.c:5,13-47`, 133 lines). The audit's "five checks implemented twice" are located in §3; the engine alone checks `dolly.host` stamps, `REQUIRES` at the row, export capture, ENTRY existence and the receipt; the JavaScript alone checks the site version, the lint rules, the transitive `INSTALL` rows a builder must supply, and `REQUIRES` edges for the view.
6. Logic moved four times, each with a reason in the record: DOLLY 2 (`c4dbe3ad`, 09-03) made the JavaScript "an earlier structural lint for fast feedback" with one check deliberately in both; DOLLY 4 (`018c5f27`, 09-27) put `hostRequirements` on the page, inherited through `FROM`/`USE`, so "metadata" could give "early checks before large snapshot downloads" (`tasks/20260926-092542-codex-host-modules/TASK.md:73-74,81`); `76a941ad` (09-30) fixed a real disagreement (JS rejected `gpu@0` with `gpu@1`, C accepted; audit-48) by folding three walkers into one and creating the parity corpus; Phase 3 (`5ec4783c`, 10-01) made hosts explicit and gave the engine the seal-time stamp check; `b60b426a` (10-02) made the engine parse without executing in a session and moved the `INSTALL` host check to the row.
7. The reflection's claims: the three line counts are exact; "a second parser whose output is a trust decision" is true for custom images, dependency builds and the `host.require` check that holds even when `DOLLY_HOST_MODULES` replaces the set (`src/browser.mjs:116,139`); "the engine already drives a fetch-on-demand loop … which amy obeys" is partly true: the loop is amy's (`src/commands/amy.c:265-290`), the engine is asked twice; "a packaged image's modules are read from the sealed artifact" is partly true: from a metadata file Node wrote from the JavaScript graph, not from the engine's receipt.
8. On the ordinary `/IMAGE/` route the engine never runs: packs are restored, and the only recipe facts the page needs (host list, openability) come from the registry and the metadata. For `dollyfile-studio` the chain is 36 recipes, 2 direct artifacts (`FROM pi-local`, `INSTALL nvim`) and 12 modules; a cold rebuild fetches the chain's metadata and recipes before any snapshot byte, then two snapshots. For a custom recipe the host is created (`browser.mjs:116`) before the Worker exists (`:145`).
9. The parser runs in five places: Node (catalog, lint, pins, views, build plan, and the packaging cross-check of the engine's `recipes.lock`, retained recipes and ENTRY against the graph in `scripts/snapshot-identity.mjs`), the page, the runtime Worker, the build service, and inside Studio's image under Janis as `dollyfile-lint` and `dollyfile-build` (`demos/studio/lint.mjs:2`, `build.mjs:2`); plus eight demo and test scripts.
10. Not found: any record of a Wasm build of the parser for the page or Node, or of a parse-only engine run before boot (the `execute = 0` path is used by `install_live` since 10-02 and by the native test harness since 09-06, nowhere else); any owner statement on two parsers; any measurement of what an engine parse before boot would cost; why `/etc/dolly/artifact` carries a host list no reader uses.

## 1. History

### 1.1 Birth: one language, two programs, and "the browser does not parse" (`9e013dd9`, 2026-08-31)

The first Dollyfile commit added `src/dollyfile.c` (1,090 lines), `src/dollyfile-view.mjs` (120 lines), `src/dollyfile-viewer.mjs` (78 lines), `scripts/image-definitions.mjs` (99 lines) and `scripts/generate-routes.mjs` (`git show --stat 9e013dd9`). The users of the JavaScript parser then: `scripts/image-definitions.mjs:5,17` (discover images, check "IMAGE name must use filename"), the viewer, and tests (`git grep 9e013dd9 -- src scripts test`). `src/browser.mjs` did not import it.

The document of that commit (`docs/dollyfile.md` at `9e013dd9`):

> "The authoritative parser and executor is the C program in `src/dollyfile.c`. It is compiled by Clang inside Dolly, installed as `/bin/dollyfile`, and run as an ordinary Dolly executable. The browser does not parse or execute build rows. JavaScript only discovers image names for routes and renders source text for the viewer." (`:8-12`)
>
> "`EXTENDS` is optional … The browser supplies only the initial recipe locator. The C engine resolves `default` to `/Dollyfile` and another parent to `/Dollyfile-<name>`, then fetches it through the same HTTP broker used for every other network request." (`:59-62`)
>
> "A custom recipe remains in the current tab and must directly extend `default`; the C engine remains the authoritative parser once the fresh sandbox starts." (`:153-155`)
>
> "The next useful evolution is a content-addressed cache or capsule format that preserves this exact row-by-row semantics. It should not reintroduce a hidden JavaScript executor or broaden the browser capability boundary." (`:165-167`)

So at birth the engine fetched a parent *recipe* itself (`EXTENDS`, text through the broker) and executed it inline; there was no image artifact to supply, and the page needed to know nothing but the root locator. The `/custom/rebuild/` route existed already (`:150`).

### 1.2 DOLLY 2 (`c4dbe3ad`, 2026-09-03): the JavaScript becomes a lint, with one check in both by design

The document: "The authoritative parser and executor is `src/dollyfile.c`. It is compiled to `/bin/dollyfile` and executes inside the sandbox. JavaScript does an earlier structural lint for fast feedback and renders the same source as linked plain text, but it does not build the image." (`c4dbe3ad:docs/dollyfile.md:7-10`). And of the SLOP tool discipline: "The fast JavaScript lint and the C Dollyfile builder perform this same small sequential check." (`:106-108`). This is the first recorded duplicate check, stated as a feature. The in-browser viewer `src/dollyfile-viewer.mjs` was deleted in this commit and `scripts/render-dollyfile-view.mjs` (static rendering in Node) was born (`git log --follow` of both).

### 1.3 DOLLY 3 (`99093739`, 2026-09-06): images become artifacts; the page computes the closure

Message: "Add FROM and COPY FROM using complete image artifacts, bind reuse to actual input digests, preserve exact exports and environment, and share published filesystem packs across images." This commit created `src/image-build.mjs` and gave `src/runtime-worker.mjs` its first import of `dollyfile-view.mjs` (`git log --follow -S'dollyfile-view'`). The first `image-build.mjs` had a `customReferences` walk that parsed the custom recipe and its `USE` modules in JavaScript to find every `FROM`/`COPY FROM` reference, then `resolve()` recursed over `definition.artifacts` from the registry to build dependencies first (`99093739:src/image-build.mjs`, shown above).

The reason is written in that document: "The browser looks for a verified local artifact, then a matching published artifact. A missing dependency is built in a disposable Wasm instance before its consumer. Builds run sequentially, and each completed artifact is saved before later stages run." and "Cache identity includes the runtime build ID, the root recipe hash, and the actual snapshot digests of its direct image inputs." (`99093739:docs/dollyfile.md:117-124`). In the same commit the native test harness `test/fixtures/dollyfile-parser.c` appeared (`34bdbc98`, `99093739`, `dd6b6a93`, all 09-06): the real `dollyfile.c` compiled by the host `cc` with stubs for `dolly_http_perform`, `dolly_write_file`, `dolly_spawn`, `dolly_wait`, and a `check` mode that calls `execute_recipe(&engine, root, 0, &exports)` (`:61`). Parse-only in the engine therefore dates from DOLLY 3, as a test hook.

### 1.11 What the history says about why, and what it does not

Reasons that are written down:

- The engine's own code arrives with the base. "The build runs the base's `/bin/dollyfile`" (`docs/dollyfile.md:136`); only a root build compiles the engine from the seed (`:357-360`; `src/process/bootstrap.c`, `docs/sources.md:21`). So `FROM` has to be resolved to bytes before anything in Wasm can read a row.
- Artifacts are the page's. DOLLY 3's "The browser looks for a verified local artifact, then a matching published artifact. A missing dependency is built in a disposable Wasm instance before its consumer" and the cache identity over "actual snapshot digests of its direct image inputs" (`99093739:docs/dollyfile.md:117-124`); the image cache is IndexedDB behind the page (`docs/browser-boundary.md:214`); builders have no local services (`:135-139`).
- Early, actionable failure: "use metadata for early checks before large snapshot downloads" (`codex-host-modules:81`); "a missing provider fails with its name and reason before the image starts" (`018c5f27` doc `:128-129`); "A custom recipe is checked before anything is built" (`origin-not-hardcoded:29`).
- Fast feedback: DOLLY 2's "earlier structural lint for fast feedback"; the lint "without a build caught recipe errors agents shipped twice" (memory 2026-10-07, cited by `audit-fable/dollyfile.md:95`).
- Agreement is a tested property, since a real disagreement was found (audit-48).

Reasons that are not written down anywhere found: why Node parses in JavaScript rather than running the engine natively (the harness proves the engine compiles natively with four stubs; no task or commit weighs using it for the scripts); whether a Wasm build of `dollyfile.c` for the page was ever considered (grep of `tasks/` and `docs/` for "wasm parser", "parse-only", "engine in node", "dry run": nothing on this subject); why the engine's receipt carries a host list nobody outside the engine reads.

## 2. What each parser does today

### 2.1 The engine (`src/dollyfile.c`, 2,282 lines)

- Input: `fetch_recipe` (`:432-444`) reads `FILE:/path` from the filesystem or a site path through `dolly_http_perform` (`fetch_memory` `:383-403`), refuses NUL and more than 128 KiB. The text of every recipe the engine executes comes either from a file the page wrote (`/etc/dolly/upload.Dollyfile`, `runtime-worker.mjs:163-165`; `/etc/dolly/Dollyfile` of the booted image for `install_live`) or from the HTTP broker.
- Lexing: `next_line` (`:1713-1720`), `strip_comment` (`:516`), `split_words` (`:564`), continuation and `FILE` bodies in `execute_recipe` (`:1739-1800`). Grammar in `process_line` (`:1511-1656`): `DOLLY 7` (`:1526`), role and name (`:1533-1547`), `FROM`/`INSTALL` (`:1553-1559`), `COPY` (`:1560-1566`), `REQUIRES` with `HOST` first and validated (`:1567-1581`), `EXPORTS` (`:1598-1623`), `SOURCE` (`:1624-1628`), `SLOP`/`RUN` (`:1630-1632`), `FILE`/`FOLDER` (`:1633-1645`), `ENTRY` (`:1646-1649`). Syntax is checked with `execute` on or off; `load_artifact`, `fetch_source`, the `REQUIRES` checks, `FILE` writes and `FOLDER` capture run only with `execute` (`:1558,1565,1584,1628,1637,1644`).
- End of recipe: missing role, name must match the file, `APPLICATION` needs `ENTRY` (`:1801-1813`), `finish_exports`, retention, `append_recipe` (`:1814-1823`).
- Meeting an image: `load_artifact` (`:1358-1476`) opens `/etc/dolly/artifacts/SHA.snapshot` and verifies its digest (`read_artifact` `:1218`), reads the receipt, checks the imported image's role against the mode (`:1373-1377`), a second pin of one recipe (`:1382-1394`), and for `INSTALL` the package's own record of rows (`install_rows` `:1330-1350`). It never fetches a snapshot. A row whose snapshot file is absent prints "`LOCATOR installs ROW first`" and returns `ROW_FIRST` (3). In a build that is a row failure: `process_line` prints "`INSTALL failed (3)`" (`:1654`), `main` returns 3 (`:2281`), the Worker throws "Dolly bootstrap failed with status 3" (`runtime-worker.mjs:268`). In a session (`install_live`, `:2200-2225`) `amy` receives the 3 (`src/commands/amy.c:270`), reads the rows from the package snapshot's own `/etc/dolly/installed` (`snapshot_rows` `:203-224`), fetches each from `https://packages.dolly.invalid/v1/packages/SHA` (`fetch_snapshot` `:226-245`), installs each as an install of its own (`:275`), then runs the engine again (`:279`). The answerer is the page's `PackageService` (`host/packages/service.mjs:19-58`): it serves only a pin the registry lists with `role === "package"` (`:32`), one at a time (`:33`), 64 per page (`:34`), bytes rebuilt and hashed from the release's packs (`:41-42`).
- Sealing (`seal_manifest` `:2108-2150`): `entry_retained` (`:2077-2106`), `check_executable_hosts` over every retained file (`:2020-2049`, `check_host_section` `:1999-2018`: a `dolly.host` record naming an undeclared module fails the build), `write_control_files` (`:1885-1983`: `/etc/dolly/recipes.lock`, `/etc/dolly/recipes/*`, `/etc/dolly/Dollyfile`, `/etc/dolly/image`, `/etc/dolly/environment`, `/etc/dolly/entry` as `DOLLYENT`), `write_artifact_receipt` (`:1016-1052`: `DOLLYART` v5 with the recipe chain, the host list at `:1030-1033`, and the exports).
- Parse-only: the comment at `:1722` ("with execute = 0 it only parses"); the one production caller is `install_live` (`:2202`), for the declared host set (`host_declared` `:1056`) and, where `nena@0` is declared, `/etc/dolly/enabled` (`:2207-2214`). The native harness's `check` mode is the other caller (`test/fixtures/dollyfile-parser.c:61`).

### 2.2 The page: every caller of the JavaScript parser and what it decides

`src/dollyfile-view.mjs` exports `inspectDollyfile` (`:311-317`), `recipeFileName`, `imageFileName`, `validName`, `unretainedPath`, `MAX_DOLLYFILE_BYTES`. `inspectRecipe` (`:172-309`) returns `hostRequirements` (validated and sorted through `host/requirements.mjs`'s `hostRequirements`, the same functions the loader uses for `dolly.host` records, `:1,231,303`), `role`, `name`, `entry`, `requirements`, `exports`, `artifacts`, `from`, `sources`, `runs`, `slops`, `files`, `folders`, `rows`. `src/dollyfile-graph.mjs` (`loadRecipeGraph`, `:15-125`) takes a `read(location)` function, parses the root and every `FROM`/`INSTALL`/`COPY` target recursively, checks each pin (`:32`), name-matches-file (`:34-37`), one location per name (`:38-41`), the role of each target (`:56-60`), that a package's hosts are declared by the installer (`:62-67`), collects the builder's `artifacts` including a package's transitive `INSTALL` rows (`:69-82`), and resolves export scope and `REQUIRES` edges (`:84-116`; "an inspection graph, not a dependency solver", `:11-13`).

| Caller | Lines | Uses the result for | Trust decision? |

### 2.5 A disagreement walked through

By the parity corpus the two parsers agree on syntax (232 cases, `test/dollyfile-parser.test.mjs:44-53`); the walk below is of a hypothetical bug, since under the threat model the attacker is Wasm, and Wasm does not control the page's parse of text whose hash the page has verified.

*The page's parser misses a `REQUIRES HOST gpu@0` line that the engine honours* (catalog or custom rebuild). `declared` lacks `gpu@0`; `createHost` builds no GPU provider; the engine runs with `gpu@0` in `engine->host_requirements`; a retained executable stamped `gpu@0` passes `check_host_section` (`:2009-2015`) and the receipt records `gpu@0`. The sealed snapshot's recipes contain the line; `describeImageArtifact` re-parses them with the same JavaScript parser, so the same miss: `host.require` passes, `admit` lacks `gpu@0`. At launch the supervisor's `checkHostAbi` refuses the executable: "host module gpu@0 is not declared by this image (REQUIRES HOST)" (`host/requirements.mjs:56-61`). Result: a session without the GPU and a program that cannot start; nothing enabled that was not listed. Fail closed.

*The page's parser finds a `REQUIRES HOST gpu@0` the engine ignores.* The page enables `gpu@0`; the engine does not record it; sealing does not fail (nothing stamped is undeclared from the engine's view only if the engine also skipped the stamp check for it; otherwise the build fails). The session has a GPU provider the engine's receipt does not name; `admit` admits GPU executables. Result: a module enabled by a line the engine did not see. This is the direction in which a parser bug widens authority; it is bounded by the registry's fixed set and the browser's own prompts (`docs/browser-boundary.md:88-95`).

*A `FROM` reference parsed differently* (say the page accepted a path the engine refuses). `prepareImageArtifacts` resolves it against the registry by location and pin (`image-build.mjs:54-56`); an unknown pin is "image pin is not present in this release" before any build. If both accept but the engine's `valid_image_reference` (`:327`) refused at the row, the Worker reports "FROM failed (2)". In neither case does a different image get loaded: the snapshot entering `/etc/dolly/artifacts/` is the one whose recipe hash the page matched (`runtime-worker.mjs:124-130`, `:173`), and the engine verifies that snapshot's digest and its receipt's last record against the pin (`read_artifact` `:1218`; `:1093-1095`).

*The receipt and the metadata disagree* (engine list ≠ JavaScript list for a packaged image). Nothing compares them: `snapshot-identity.mjs` checks the lock, the retained recipes and ENTRY, not the receipt's host list. At `INSTALL` time the engine uses its receipt list for the package being installed (`:1105-1114`); the page used the JavaScript list to enable modules. A package whose receipt names a module the installer's recipe text does not name is refused by the engine even if the page enabled it (unless `nena@0` and `/etc/dolly/enabled`).

### 2.6 Under the threat model: which inputs come from Wasm

From bytes the page fetched or holds itself: the registry (a static module of the release, generated in Node); the catalog recipes (fetched `no-store`, hashed against the registry, `image-artifact.mjs:23-34`); a custom recipe (typed into the page, held in `sessionStorage`, `custom-dollyfile.mjs:43`); the recipes a custom graph references (same-origin `fetch`, pin-checked); packaged metadata and packs (hashed, `:165,173`); IndexedDB artifacts (re-described and hash-compared, `:233-245`).

From Wasm: the sealed snapshot after a rebuild, copied out of kernel memory (`runtime-worker.mjs:206-214`): `/etc/dolly/Dollyfile`, `/etc/dolly/recipes/*`, `/etc/dolly/artifact`, `/etc/dolly/entry`, `/etc/dolly/image`, `/etc/dolly/environment`, and every retained file. Of these the page verifies: the root recipe by hash against its own `recipeSha256` (`image-artifact.mjs:181`); every chain recipe by the pin in its parent (`dollyfile-graph.mjs:32`), so the whole chain is anchored in the page's hash; `/etc/dolly/image` against the route (`runtime-worker.mjs:290-293`); `/etc/dolly/entry` structurally only (`src/image-entry.mjs`). It does not read the receipt's host list. A compromised build therefore cannot widen the module set the page derives (it would need a second recipe text with the same SHA-256); it can choose the ENTRY program and every file, which is the userspace's own authority; and in a session it can ask `packages@0` for any published package's bytes, "ordinary sandbox data" (`docs/browser-boundary.md:132`). `amy`'s status-3 loop runs in Wasm; what it can obtain is bounded by the registry (packages only), the one-at-a-time rule and the 64-per-page quota.

The AGENTS.md sentence "A page gives an image the host modules its recipe lists" (`AGENTS.md:50`) is implemented as: the page reads the list from recipe text it has hashed itself, never from a Wasm-written field; the review map says "Build and custom-session policy comes from trusted browser state, never from recipe or snapshot contents" (`docs/browser-boundary.md:140-142`) of the HTTP policy, and the same holds for the module set in the sense above.

## 4. Each claim of the reflection, checked

**"`dollyfile-view.mjs` 317 lines, `dollyfile-graph.mjs` 125, `image-build.mjs` 98."** True in this tree (`wc -l`).

**"The page parses the recipe language in JavaScript to compute a build's closure and its trust set (`hostRequirements`, `from`, `entry`)."** True. Closure: `prepareImageArtifacts` (`image-build.mjs:26-92`). Trust set: `loadImageHostRequirements` (`:95-98`) into `createHost` (`browser.mjs:110-123`); `from` at `runtime-worker.mjs:118-119`; `entry` at `browser.mjs:115` (openability only; the program run is the engine's `/etc/dolly/entry`). Not said by the reflection: the same list is also derived from the sealed snapshot by the same JavaScript (`image-artifact.mjs:184-191`), and the engine's own sealed list is unread; and the HTTP policy's bootstrap allowlist is the parser's output too (`browser.mjs:103-109`).

**"A second parser whose output is a trust decision."** True for the module set of custom images, rebuild routes, dependency builds, and the `require` check under `DOLLY_HOST_MODULES` (`browser.mjs:139`); for catalog images the decision is made in Node and the page checks two JavaScript-derived copies against each other. The audit's own confidence was "medium (parser not read in full)" (`boundary.md:55`). What the decision rests on under the threat model is in §2.6: hash-verified recipe text, never a Wasm-written field.

**"The engine already drives a fetch-on-demand loop for `INSTALL` rows (`ROW_FIRST`, `src/dollyfile.c:1329-1350`), which amy obeys."** Partly. The lines are right (`enum { ROW_FIRST = 3 }` at `:1329`, `install_rows` `:1330-1350`). The engine does not loop or fetch: it exits with 3 once, naming one row. The loop is amy's (`amy.c:265-290`): read the rows from the snapshot's record, fetch each through `packages@0`, install each separately, ask the engine again. It exists only in a session (`install_live`), for `INSTALL` rows of packages, after ENTRY, in an image that declares `packages@0`; in a build the same 3 is a failure (`:1654`; `runtime-worker.mjs:268`), and the builder has no package service (`docs/browser-boundary.md:135-139`). The page's answer to each fetch is gated by the registry (`service.mjs:32`), which the JavaScript parser wrote.

**"A packaged image's modules are read from the sealed artifact (`src/runtime-worker.mjs:111`), a custom one's from the page's own parser (`src/browser.mjs:114`)."** Lines right. Partly on substance: `snapshotMetadata.hostRequirements` at `:111` is the metadata file `dist/dolly-IMAGE-system-snapshot.mjs`, written by `scripts/build-system-snapshot.mjs:159` from the JavaScript graph in Node, and required to equal the registry's list (`image-artifact.mjs:54`); the engine's sealed list in `/etc/dolly/artifact` is not what is read. `browser.mjs:114` is one of two custom reads: the host set comes through `loadImageHostRequirements` at `:110` (the graph), `:114` gives `entry` and `image`.

**Section 2's "the page reading the declaration from two sources: the sealed artifact for packaged images, its own JS parser for custom ones" and the proposal "The page reads `REQUIRES HOST` from the sealed artifact only; a custom build needs the runtime line and nothing more before sealing."** The two sources are both the JavaScript parser's output (§2.4). For the proposal's second half: a custom build's host is created at `browser.mjs:116` before the Worker at `:145`; its set is the declared list plus `buildHost`, of which only the runtime and the three build modules are needed to build (`buildHostFor`, `host/modules.mjs:14`, is what a dependency build already uses). What else the declared list adds before sealing: the rebuild route's host set is also the session's, since the page does not disable modules after sealing (`runtime-worker.mjs:218-219` only `require`s and `admit`s).

**"The engine asks for every pin it lacks (`FROM`, `COPY`, `INSTALL`) and the page hands over bytes by pin, as `packages@0` already does; the page then parses no recipe, and `dollyfile-view.mjs` stays a script-side tool."** A proposal; §5 walks it. ### What would have to exist, and what would no longer be needed

Would have to exist, by the walk above: a way for the base to be present before the engine runs that does not require the page to know `FROM` (an engine outside the base), or the page keeps resolving `FROM`; a bytes-by-pin service available to builders for `INSTALL`/`COPY` rows (a new authority row in the review map; `packages@0` serves packages only, one at a time, 64 per page); an engine output of a recipe's facts the page can read for the session's set, in a form the page verifies (today it verifies text by hash; the receipt is binary and unverified by the page); a parse before boot for custom recipes, which needs a booted kernel and so a module set first; for Node, nothing new, since the reflection keeps the script-side parser.

Would no longer be needed on the page, if every one of those existed: `prepareImageArtifacts`'s recursion over `definition.artifacts` and the custom graph (`image-build.mjs:11-22,51-92`); the `describeImageArtifact` graph (`image-artifact.mjs:184-191`), replaced by a receipt reader; `loadImageHostRequirements` for custom images. Would remain: `inspectDollyfile` on the page for the runtime line and `ENTRY`-or-not before boot, the registry reads, the parser in Node, in Studio's image, in the build service's 400 check, and the parity corpus for the two that remain.

Where the JavaScript parser is the only thing that can know a fact at the moment it is needed, exactly: the module set of a custom image before any Wasm exists (`browser.mjs:116` precedes `:145`); the `FROM` base of any build before the kernel can be resumed from it (`runtime-worker.mjs:118-119,187-190`); the host list and openability of a packaged image on `/IMAGE/`, where no engine runs at all (`runtime-worker.mjs:108-113,229-266`); the dependency order and staleness of 130 images in Node before any browser starts (`build-system-snapshot.mjs`); which pins `packages@0` may serve (`service.mjs:32`); the HTTP policy's bootstrap allowlist (`browser.mjs:103-109`).

## 6. What could not be found out

- **Whether a Wasm build of `dollyfile.c` for the page or Node was ever considered.** No task, commit or document mentions it (grep of `tasks/` and `docs/` for the phrases in §1.11). The native harness shows the parser compiles outside Wasm with four stubs; what a Wasm build would cost in size, boot time and a new output format was not measured and is not recorded.
- **Why Node parses in JavaScript.** The only statements are the founding one ("JavaScript only discovers image names for routes") and DOLLY 2's "fast feedback"; no record says "because no runtime exists yet" or weighs the native engine for the scripts.
- **Why the receipt carries a host list no JavaScript reads**, and why `describeImageArtifact` re-parses recipes instead of reading it: `76a941ad`'s message does not say; the receipt's host list came with `5ec4783c` for the `INSTALL` check.
- **The owner's view on two parsers.** `audit-50` listed it as a pressure point and the v5 proposal was rejected; `audit-48` was closed by making them agree; the owner's words on this subject were not found. The owner's one recorded decision near it is the static frontend ("Classic static files at the right locations"), which keeps generation in Node.
- **What an engine parse before boot would cost.** A root build compiles the engine from the seed before the first row (`bootstrap.c`); a `FROM` build resumes a base of tens to hundreds of MiB first. Neither time was measured here; the slop-and-run investigation holds build timings for other purposes.
- **Whether the two parsers disagree on any live recipe.** The parity corpus is 232 synthetic cases; `snapshot-identity.mjs` checks the engine's lock, recipes and entry against the graph for every packaged image at every `npm run image`, which is a parity check over the live catalog for those three facts; no equivalent exists for the host list (receipt vs metadata), so a live disagreement there would go unnoticed by the tree's checks.
- **How often `ROW_FIRST` fires in practice**, and whether a build has ever hit it (the message "installs X first" in a build log): build logs are not in the repository.
- **Studio's copy of the parser.** Whether `src/dollyfile-view.mjs` in Studio's image is byte-identical to the checkout's at release time is asserted by `demos/studio/test/studio.test.mjs` per the lsp task; whether that image is rebuilt when only the parser changes was marked "to be checked first" in `tasks/20261013-160335-stale-words/TASK.md:23-24` and is still open.
