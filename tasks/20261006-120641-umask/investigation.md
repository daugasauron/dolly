# Dolly's files without a stored mode: the investigation

Read at `/home/daug/dev/dolly/work/rust` (branch `integrate/round-1013`, head `2fc79ded`, 2026-10-14), whose history is `main`'s; the branches `core/file-modes` (`c17b186e`), `core/file-modes-2` (`0e4b4c26`) and `core/polish` were read with `git show`/`git diff`. Upstream sources were read in the shared cache (`.cache/git-e9019fca…`, `.cache/make-4.4.1-source`, `.cache/sbase-c546c3a5…`). Nothing was built or run; measurements quoted are those recorded in tasks and commits, with their dates. Line numbers are of this tree unless a commit is named. The reflection's tree is `d89bca74`.

## Summary (findings, no advice)

1. `chmod` has been a stub since the first commit: `0d224977` (2026-08-29) has `dolly_chmod` as `return access(path, F_OK)` and `dolly_umask` returning 0 (`src/dolly.c:506-514` there). The roadmap of `aa0e63c0` (2026-08-31) lists "permission and user models inside a single disposable sandbox" among "Explicit non-goals until evidence changes"; that roadmap was deleted on 2026-09-08 (`18275741`), so on 2026-09-30 the design was cited by commit, not read in the tree.
2. The caller's creation mode did reach WasmFS while commands ran in the kernel's memory (musl's `open`/`mkdir` into WasmFS). It stopped arriving on 2026-09-05 with private processes (`b95459ce`: `openat(..., 0666)`, `mkdirat(..., 0777)`, a path request with no mode); the same commit wrote today's libc comment "Dolly has no permission boundary inside its shared userspace".
3. The one day of real modes: `26277ef5` (2026-09-30 19:48) added `PATH_SET_MODE` 44 and `FD_SET_MODE` 58 and let WasmFS enforce what `chmod` stored, answering audit-04 ("chmod ... report success without doing anything"). `d41df0cb` (23:02) removed them: "That reversed a documented design", citing the roadmap, the libc comment, `fs-record.h`'s "Modes are compatibility metadata, not an execution permission model" and the side-module stub; the audit task was closed "By design, not a bug. Dolly has one user and no permission bits (owner, 2026-09-30)". The reason recorded the same evening (`05e6bd8b`, `docs/architecture.md:55-58`): "Every process is the same principal and the containment boundary is the browser, so modes would protect nothing."
4. Today the kernel passes a fixed 0666/0777 (`src/process-kernel.c:1963`, `:2009`); WasmFS's own default mask makes them 0644/0755; image restore writes 0777 so every image file reports 0755 (`src/fs-record.h:344`; measured 2026-10-06, `20261006-005303-ls-long-format`). `stat` passes WasmFS's twelve bits through (`:1037-1038`). `chmod`, `fchmod`, `chown` check existence and return 0 (`src/process/libc-adapter.c:934-975`); `access` ignores `R_OK|W_OK|X_OK` (`:994-1004`); `umask` is a libc static (`:767-770`); `mkdir` and `open` drop the mode (`:519-520`, `:1007-1011`). The kernel starts any readable regular file that is a Wasm module or `#!` text (`:388-487`); no code reads an x bit anywhere.
5. The sockets module depends on the stub: a bound path is a regular file the kernel marks with the sticky bit, "which no process can set: chmod changes nothing" (`src/process-kernel.h:85-88`; `host/sockets/kernel.c:191-193`, `:218`), and `encode_stat` masks that bit out of such files (`:1038`).
6. The umask task was filed on 2026-10-06 by the integrator, with "Decision (integrator, 2026-10-06 night): Slop gets `umask`, but only with a real effect". `core/file-modes` (2026-10-06/07, unbuilt) and its replay `core/file-modes-2` (2026-10-08, built on a 15-image chain, 24 suites in both browsers, GNU Make's unchanged `configure` to exit 0 in 49 s) store nine bits in WasmFS's inode, enforce WasmFS's read/write rules, add operations 58 and 60, turn the path request's `reserved` word into `mode`, and move images and sessions to format 3. Core source: 16 files, +354/−121; the whole branch 126 files, +1520/−588, most of it pins and tasks. No owner words for or against the branch were found; it was "Deferred to 0.1.1" by the integrator's lean cut after the owner's "keep it lean" (2026-10-08), left out of 0.1.1 and 0.1.2, and on 2026-10-13 the task says a merge "is a day in a full tree with the large build slot and then a catalog round".
7. What an autoconf `configure` needs of modes, measured: two commands that exit 0. `config.guess` and `config.status` run `(umask 077 && mktemp -d ...) || (umask 077 && mkdir "$tmp")` and check `test -d`, not the mode; `configure` ends with `chmod +x $CONFIG_STATUS || ac_write_fail=1` (Make's `configure:15845`). Slop refuses `umask` by name (`src/slop.c:3078`, since `a0f1d9cc`, 2026-10-05) and no image has `chmod` (sbase's is left out of the tool list, `Dollyfile-system-tools:25-30`). Measured 2026-10-13: Make's `configure --build=...` runs 200 checks then stops at `chmod: command not found`; without `--build` it stops at `umask 077` in `config.guess`. No check in Make's `configure`, `install-sh` or `config.guess` relies on a mode being enforced (section 4).
8. Git writes `core.filemode false` at `init`/`clone` because its probe (`setup.c:2589-2601`) sees `chmod` change nothing; a new file is then recorded 100644 (`read-cache.h:15-18`), a cloned 100755 keeps its recorded mode but is checked out 0644 (`entry.c:88`, the mode dropped by `open`), and `status` ignores mode changes (`read-cache.c:324-326`). Dolly's `tar` never reads the header's mode field (`src/commands/tar.c:144-145`, `:206`); `install -m` is parsed and dropped (`src/commands/install.c:192-194`); `cp` has no `-p` (`cp.c:242`). tmux needed `-DTMUX_SOCK_PERM=0` because `mkdir(0700)` reads back 0755 (`demos/tmux/Dollyfile-tmux:51-53`, `:66`).
9. Thirteen recipes say "Slop does not run upstream's configure" and write its answers by hand (14 configure scripts: less, libevent, xz, jq and Oniguruma, unzip, zip, mandoc, sqlite, bc, byacc, reflex, tmux, pkgconf); ICU and libsodium are compiled as source directories ("have only autotools, which Slop cannot run"); GNU Make, CPython, libffi and Emacs are configured on the host in the emsdk container. None of those comments names `chmod` or `umask` as the reason; the configure survey (2026-10-06) found seven Slop fixes (all on `main` since v0.1.0) plus `umask` make four `configure` scripts match Bash natively, after which the stops inside Dolly are modes, `config.guess`'s name for Dolly, `exec`, and cost.
10. The reflection's "store the twelve bits and enforce nothing": the branch stores nine and enforces, because WasmFS enforces what its inode holds (the branch's reading of Emscripten 6.0.8 `syscalls.cpp`); storing in the inode without enforcing needs a kernel bypass or a side table, which no commit has written. "A mode in the reserved word" is exactly the branch's `process.h` change. "`SET_TIMES` becomes `SET_ATTRIBUTES`": the two times packets have a `reserved` word and an `OMIT` flag, so the packet sizes could stay; it is still a `process.h` edit and so a restamp of every executable, as the branch's is. "git commits every file as 644; tar and install -m lose the x bit": true by reading for new files, tar and install; not measured on `main` by any test.

## 1. History

### 1.1 Before the one-user decision (2026-08-29 to 2026-09-29)

- `0d224977` (2026-08-29, the prototype). Commands ran in the kernel's memory through Emscripten's musl over WasmFS, so `open(path, O_CREAT, 0600)` stored 0600 minus WasmFS's mask: the first filesystem did store the caller's mode. The chmod/umask shim for side modules was a stub from this commit: `int dolly_chmod(const char *path, mode_t mode) { (void)mode; return access(path, F_OK); }` and `mode_t dolly_umask(mode_t mask) { (void)mask; return 0; }` (`src/dolly.c:506-514` at `0d224977`; `:951-959` at `aa0e63c0`).
- `aa0e63c0` (2026-08-31). `docs/roadmap.md:215-221`: "## Explicit non-goals until evidence changes — multiprocessing and job-control fidelity; — permission and user models inside a single disposable sandbox; — raw socket compatibility; — complete Node, npm, or Linux emulation; — performance optimization before correctness profiles exist". `18275741` (2026-09-08, "Refresh and condense documentation; add MIT license") deleted the roadmap, so this sentence was not in the tree on 2026-09-30.
- `07a3cf1e` (2026-09-03). The earliest `test` with "Dolly has no execute permission bits" and the earliest `install` whose `-m`, `-o`, `-g` are "syntax-only" (`git log -S`).
- `b95459ce` (2026-09-05, private processes). The kernel's `PATH_OPEN` and `PATH_CREATE_DIRECTORY` took no mode: `openat(directory, path, flags, 0666)` (`src/process-kernel.c:1711` there), `mkdirat(directory, path, 0777)` (`:1754`). The libc adapter: `__syscall_chmod` returns 0 for any path (`:605-609`), `__syscall_umask` a static (`:598-602`), with the comment that is still there today: "Dolly has no permission boundary inside its shared userspace. Keep umask as process-local libc compatibility state without turning it into a kernel or browser capability." From this commit the creation mode a program asked for stopped reaching the filesystem.

The decision of 2026-09-30 says what is not wanted (a permission model, enforcement, a uid policy) and gives the reason (one principal, the browser is the boundary); it does not speak of a stored but unenforced bit, and `fs-record.h`'s sentence it cites ("compatibility metadata") describes a bit that is stored and not enforced.

### 1.7 What the history says that the reflection does not

- The stub is older than the private-process ABI; what the ABI removed on 2026-09-05 was the creation mode, not `chmod`.
- Real modes existed for three hours on 2026-09-30, with enforcement, and were removed for reversing a design, with a security-model reason written the same hour.
- The branch answers the audit-04 expectation and the autoconf need and was built and measured; it is more than "store": it enforces, because WasmFS does.
- The one dependency on today's behaviour that is code, not prose, is the sockets module's sticky-bit marker (2026-10-08), written after the decision and relying on it.
- The "two commands that exit 0" are what the measured `configure` stops need; the decision to store something behind them is the integrator's of 2026-10-06, taken because a command that changes nothing was judged to be what `AGENTS.md` rules out.

## 2. What happens today

### 2.1 What `stat` reports

- `encode_stat` (`src/process-kernel.c:1024-1044`): `response->mode = st_mode & 07777`, or `& 0777` for a socket node (`:1037-1038`); `file_type` from `stable_file_type` (`:1012-1022`), where a regular file with the sticky bit is reported as a socket (`:1013`). `decode_stat` in libc rejects a mode above 07777 (`libc-adapter.c:556-558`).
- A regular file a process creates: the kernel passes 0666 (`:1963`), WasmFS applies its default mask 022 (the kernel never calls `umask`; `grep umask src/dolly.c src/libc-host.c` is empty): 0644. A directory: 0777 (`:2009`) minus 022: 0755. A file or directory restored from an image or session: `open(..., 0777)` (`src/fs-record.h:344`) and `mkdir(..., 0755)` (`:289`, `:338`): 0755 each. A symbolic link: 0. `/dev/null`: 666. These are the figures measured on 2026-10-06 (1.3). A pipe or socket descriptor: `FD_STAT`'s default `.mode = 0600` (`:1931-1934`); the terminal: WasmFS's device mode with `file_type` forced to `CHARACTER_DEVICE` (`:1939-1941`).
- "Executable" is decided by nothing: `ls -l` prints `-rw-r--r--` for a fresh `a.out` and `-rwxr-xr-x` for every image file (1.3), and neither says whether the file runs. The kernel decides at start by content: `read_image_bytes` reads the file through `dolly_fs_read_file` (`:388-396`; `ENOEXEC` under 8 bytes), `read_image` accepts the eight-byte Wasm header or a `#!` line naming an absolute in-Wasm interpreter, nested at most `DOLLY_KERNEL_SHEBANG_DEPTH` (`:398-487`; `ENOEXEC`, `ELOOP`). The process Worker then instantiates it; a module that fails to instantiate is "refused" with status 126 (`src/process-supervisor.mjs:733-745`). No path reads an x bit; no `EACCES` for a mode exists.

### 2.2 The calls in the libc adapter and the kernel

| Call | Adapter | Kernel | Result |
| --- | --- | --- | --- |
| `open(O_CREAT, mode)` | `__syscall_openat` ignores the variadic mode, "The mode is not part of Dolly's ABI: there is no permission model." (`:519-520`) | `openat(..., 0666)` (`:1963`); the path request's `reserved` must be 0 (`:963`) | 0644 |
| `mkdir(mode)` | `(void)mode` (`:1007-1011`) | `mkdirat(..., 0777)` (`:2009`) | 0755 |
| `chmod`, `fchmodat`, `fchmod` | `existing_path`/`existing_descriptor`: a `PATH_STAT`/`FD_STAT` (`:934-962`) | none | 0 if the target exists, else `ENOENT`/`EBADF`; nothing changes |
| `chown`, `fchownat`, `fchown` | the same (`:964-975`) | none | 0 for any uid/gid if the target exists |
| `umask` | a static, 022 at start, per process, not inherited (`:764-770`) | none | the previous value |
| `access`/`faccessat` | `R_OK|W_OK|X_OK` validated then ignored; a `PATH_STAT` (`:994-1004`) | none | 0 for anything that exists |
| `getuid` etc. | 0 (`:759-762`) | | |
| `stat`'s `st_uid`/`st_gid` | WasmFS's, 0 | | |

So `chmod` and `chown` report the truth about existence and are silent about the mode they were given; `access(X_OK)` on a text file and `access(W_OK)` on anything return 0. Against the porting rule ("an unimplemented operation cannot return success"): `chmod` returning 0 is what audit-04 reported, and what `d41df0cb` chose to keep with the ENOENT fix, calling it the documented design; `tasks/20261005-131642-big-picture:110-111` names `install -m` and `chmod` under that rule again on 2026-10-05, and the ls task of 2026-10-06 applied the rule to refuse a `chmod` command while keeping the libc call. The emacs task records that Emacs's configure, run on the host, claims `HAVE_FCHMODAT`; `Dollyfile-less:25` does the opposite: "Not claimed: fchmod (there are no permission bits)".

### 2.3 Slop

- `umask`: refused by name, "Dolly has no permission bits", status 2 (`src/slop.c:3072-3081`); `docs/slop.md:34-35` files it under "POSIX, but Dolly's process model gives it no meaning". No `chmod` builtin; `chmod` is "command not found" (127).

## 4. The reflection's and the task's claims, checked

**"`encode_stat` passes mode bits through (`process-kernel.c:963-964`) but nothing sets them (`__syscall_chmod` no-op, `libc-adapter.c:948-962`) and `PATH_OPEN` has no mode field."** True; the lines are right at `d89bca74` (`:1037-1038` and `:948-962` here). "No mode field": the path request has a `reserved` u32 at the mode's place (`process.h:586-592`), which the kernel requires to be zero (`:963`).

**"Storing twelve bits is mechanism; enforcing is policy, and the one-user decision only argues against enforcing."** Two facts bear on it. (1) Today's `stat` already passes twelve bits (`07777`), and one of them, the sticky bit on a regular file, is used by the kernel as a socket marker on the premise that no process can set it (2.7): a stored, settable twelfth bit changes what `stat` and `connect` mean for such a file unless the marker moves. The branch stores nine ("Set-user-ID, set-group-ID and sticky are not stored: `chmod` and creation drop them, as POSIX allows"). (2) The one place to store bits that the branch found is WasmFS's inode, and WasmFS enforces what it stores: "opening needs a read or a write bit in any class; `mkdir`, `unlink` and `rename` need a write bit on the parent" (the branch's reading of Emscripten 6.0.8 `syscalls.cpp`, confirmed by its browser probe: "no read bit, no `cat` and no start (126); no write bit, no append or truncate"). "Store and enforce nothing" therefore needs either a kernel that lends bits around every WasmFS call (the branch wrote one such function, `dolly_fs_open_for_capture`, for capture alone) or a mode kept outside the inode. Whether the decision of 2026-09-30 "only argues against enforcing": `d41df0cb` removed storing and enforcing together and cites "compatibility metadata" as the design, which is a stored, unenforced bit; `docs/architecture.md:57` adds "Execute bits never select programs". Both readings have text.

**"Smallest: a mode in `dolly_process_path_request`'s `reserved` word for `OPEN|CREATE` and `CREATE_DIRECTORY`."** True that the word exists and is the right size; it is what `706d559e` did ("The path request's reserved word becomes the mode"), with the kernel accepting a non-zero word only for those two operations and `PATH_SET_MODE`. It is a `process.h` edit (the comment and the field name), so a restamp of every executable under the exact-bytes identity; a kernel that read the word without the header changing would be a silent ABI change, which `0d42f4e2`'s decision rules out.

**"`SET_TIMES` becomes `SET_ATTRIBUTES` carrying mode."** `dolly_process_fd_times_request` (`process.h:350-355`, 40 bytes) and `dolly_process_path_times_request` (`:594-602`, 48 bytes) each have a `reserved` u32, and each timestamp has `flags` with `DOLLY_PROCESS_TIME_OMIT` (`:273`; honoured by the kernel, `src/process-kernel.c:1067-1076`). So a mode and a "set the mode" flag could ride in the existing bytes with both times omitted; the sizes stay. It remains two operations (the fd/path twins) and a `process.h` edit. The branch chose one new operation instead (58, a path request whose empty path names the descriptor) and one for the mask (60). Neither form is smaller than the other in rebuilds: both restamp everything. The reflection does not say where `umask` lives.

**"Today `git` commits every file as 644 and `tar`/`install -m` lose the x bit."** By reading (2.5, 2.4): git, true for new files and for checkouts, with the nuance that a cloned 100755 stays 100755 in the index and in commits; tar, true (the field is never read); `install -m`, true. Not verified on `main` by any test or recorded measurement; the branch's measurements are on the branch.

**The task's "stops where it needs file modes: `chmod` and `umask`."** Measured (1.5). What the two stops need, read in the scripts: `umask` must not fail (`config.guess:119-121`, `configure:16107-16112`, each `|| ... || exit`); `chmod +x` must exit 0 (`configure:15845`); `test -x` must be true of `config.status` afterwards (`as_fn_executable_p`), which it is today for any regular file. The mode of the temporary directory is never checked by the scripts. Which of the stored designs, or none, satisfies "needs" is the design question; the scripts themselves ask for the two commands and `test -x`.

**"Every configure requires `test -x /` of its shell" (`ae118619`).** True of autoconf's shell test and fixed on `main`.

## 5. What a change would mean, on real cases

Observations only, each through three states: **today** (`main`), **the branch** (`core/file-modes-2` as it is), and **the reflection's smallest form** (nine or twelve bits stored at creation through the `reserved` word, settable through a `SET_ATTRIBUTES`-style packet, nothing enforced; `umask` not specified, taken here as libc-local as today unless said).

**(a) An unchanged `configure` creating and running `config.status`.** Today: with `--build`, 200 checks, then `chmod +x config.status` is "command not found", `ac_write_fail=1`, "write failure creating ./config.status"; without `--build`, `config.guess`'s `umask 077` first. Branch: exit 0, 49 s; `config.status` 0755 and runs again; its `(umask 077 && mkdir)` gives 0700 because the mask is in the process record and `mkdir` is a child. Smallest form: needs a `umask` builtin that exits 0 (any effect), a `chmod` program (sbase's, calling `fchmodat` into a real operation), and `test -x` of a 0755 file true (it is, by type, today; by bits under the form). If `umask` stays libc-local and uninherited, `(umask 077 && mkdir "$tmp")` still exits 0 and `test -d` passes; the directory is 0755 rather than 0700, which no autoconf check reads. After `configure`: `make` needs `exec` in `install-sh`'s subshell and `set -f` (survey), unchanged by modes. Rebuilds: the branch's and the smallest form's both edit `process.h`; a form that only adds the Slop builtin and a `chmod` command that validates and exits 0 edits no contract, and is the form the ls task refused on 2026-10-06 under `AGENTS.md`.

**(b) `git clone` of a repository with an executable script; `git status`; `git add` of a new script.** Today: `core.filemode=false` at clone; the script is 0644 and runs; `status` clean; a new script is committed 100644. Branch (measured): `core.filemode true`, 100755 tracked; checkout passes 0777 through `open` and gets 0755; `add` records x. Smallest form: Git's probe needs only that `chmod` is stored and `lstat` shows it, so the same as the branch. Who relies on today: no test; `tasks/20261005-131650-userspace-gaps` names `git archive` as the way to make a tar, whose members would carry 0644/0755 as `stat` says in each state.

**(c) `tar -xf` of an archive with executables, then `./configure` or `./script`.** Today: the core `tar` never reads the mode; everything is 0644 and 0755; the script runs because nothing checks x (Slop finds a regular file, the kernel reads a `#!` line).
