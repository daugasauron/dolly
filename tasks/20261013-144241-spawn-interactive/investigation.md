# `SPAWN_INTERACTIVE`, `SPAWN_FOREGROUND`, and where the rule for Ctrl+C at a shell lives: the investigation

Read on `work/rust` (`integrate/round-1013`, head `3c50a513`, 2026-10-14); history shared with `main`; tasks at `/home/daug/dev/dolly/tasks/`. Line numbers of `src/`, `host/`, `include/` and `test/` files are of that tree. Nothing was built or run; every number comes from `git`, `grep` and the files.

## Summary

1. The rule "the shell is spared while its command runs" is as old as the first commit (`aa0e63c0`, 2026-08-31), older than the process kernel, and has had four different keys: a pid the kernel set when it launched Pi or Slop by name (08-31); a page option the runtime worker chose by program path (`path === "/bin/slop" || path === "/usr/bin/pi"`, 09-05); the spawn flag set by `/bin/foreground -i` from the image's own script (09-06, "the browser does not recognize Slop, Pi or recovery paths"); and, for pseudo-terminals, no key at all: the holder the other holders descend from (10-12).
2. What the flag decides also changed once. Until 2026-10-01 the flag plus the owner's children decided whether Ctrl+C is SIGINT or input ("Foreground Ctrl+C remains a lifecycle operation, not mutable terminal state", `runtime.h` then). The owner's ISIG decision (`ae86e8c0`, task `20261001-000500`) moved that to termios; since then the flag decides only who in the foreground tree takes the signal.
3. Today the kernel validates, stores and exports the INTERACTIVE bit and never reads it again (`src/process-kernel.c:694-698, 723, 2528-2531`); the supervisor reads it twice: to choose SIGINT targets (`src/process-supervisor.mjs:277`) and to give a large exiting process a 500 ms reclamation window (`:671`). The reflection does not mention the second use.
4. The display terminal's sparing rule is implemented once, in JavaScript, keyed on the flag. The pseudo-terminal's sparing rule is implemented once, in C, keyed on descent among a slave's holders (`src/process-kernel.c:2422-2435`, `host/pty/kernel.c:109-112`). They are two rules, not one rule twice, and they differ for a foreground owner without `-i`.
5. `src/process-kernel.c:180-194` (the reflection's second implementation) does not spare anybody: it finds the foreground owner by the FOREGROUND bit and publishes whether Ctrl+C is SIGINT (ISIG).
6. A reverted experiment exists (`01bd1f6f`/`f91e1aef`, 2026-09-30): making a childless interactive owner take SIGINT. It was reverted because "the rule changes every interactive owner, not only Slop. Pi … would end Pi"; the ISIG decision then solved Pi's half by raw mode. Nothing in the history tried `SIG_IGN` as the mechanism, process groups, or a per-process foreground; Dolly has none of these (`docs/process-model.md:223-224, 371`).
7. Callers that pass INTERACTIVE: `/bin/foreground -i` (34 lines, `src/commands/foreground.c`), Codex's launcher (`demos/codex/launch.c:75`), and one line of a test fixture. 51 of 51 `ENTRY` rows go through `foreground -i /bin/slop`; 9 script rows start a program with `-i`, 10 without. Slop, `timeout`, `time`, `env`, `xargs`, `posix_spawn` and Janis's `child_process` all spawn with flags 0.
8. POSIX has two models, not one: a job-control shell is spared by not being in the terminal's foreground process group (the flag is Dolly's stand-in for that), and a non-job-control `sh` receives SIGINT with its child, ignores or handles it, and decides afterwards from the child's wait status (Slop's `wait_command` already does the second half, `src/slop.c:3031-3035`). `SIG_IGN` alone is neither model.
9. Slop's own SIGINT path already survives the signal: a recording handler, `waitpid` retried on `EINTR`, the launch-window rule (`892c163d`). What the flag states that no disposition states: that a Ctrl+C the child handled and survived (Python's REPL, `less`, a game) is not a Ctrl+C for the shell; without the flag Slop's `interrupt_requested` is set by every such press and `spawn_command` cancels the next command of the list (`src/slop.c:3053-3057`).
10. Not measured anywhere: Slop receiving SIGINT concurrently with a child that handles it; the 500 ms deadline on a parent that ignores; Pi's and Codex's terminal mode while a tool runs. The task's measurement is stated precisely in section 6.

## 1. History

### 1.1 Before the process kernel: a pid the kernel set itself (`aa0e63c0`, 2026-08-31)

Commands ran inside the kernel's own memory with exit frames; cancellation was a cooperative checkpoint the compiler inserted on control-flow edges (`src/dolly.c` at that commit, `:743-757`: "Dolly's C/C++ target inserts this callback on control-flow edges. It is an in-runtime cancellation safepoint"). The kernel launched Pi, then Slop, by name and marked the one it launched:

> `// Pi is Dolly's primary agent-facing interface. It is the first resident terminal program, and a plain Slop shell remains available as a recovery environment after Pi exits.` (`:1638-1640`); `launching_interactive_shell = 1; int pid = dolly_spawn("/usr/bin/pi", …)` (`:1642-1643`); `if (is_interactive_shell) interactive_shell_pid = process->pid;` (`:1420`).

The rule, in two places already: the page saw the foreground as interruptible only when `pid != interactive_shell_pid` (`:179-180`), and `dolly_interrupt_poll` answered 0 for `active_process_pid == interactive_shell_pid` (`:736-740`). `dolly_kill` accepted only SIGINT and only for the foreground (`:1038-1050`). The prototype before it (`0d224977`, 08-29) has no such word.

### 1.2 Private Workers: a page option chosen by path (`b95459ce`, 2026-09-05)

Processes became Workers; the supervisor took `spawn(path, args, { foreground, interactive })` and kept `foregroundRootPid` itself. Its `#updateForeground` told the kernel whether the foreground was interruptible: `root.interactive ? Number(hasForegroundJob) : 1` (supervisor at that commit, `:240-245`), and `#interruptForeground` delivered to the descendants of an interactive root and to a non-interactive root itself (`:259-268`). The kernel kept only two setters (`dolly_process_foreground_set(pid, interruptible)`, `foreground_clear`, `src/dolly.c` then `:867-899`). Who said `interactive`? The runtime worker, by program path:

> `const interactive = path === "/bin/slop" || path === "/usr/bin/pi";` (`src/runtime-worker.mjs` at `b95459ce:211`); `.dollyrc` ran as `{ foreground: true, interactive: true }` (`:218-222`).

The reclamation window for "large interactive memories" (`largeInteractiveProcessBytes`, 128 MiB, 500 ms) was born in this commit and still reads the same bit (`git log -S'largeInteractiveProcessBytes'`: only `b95459ce`).

### 1.3 The spawn flag and `/bin/foreground` (`3f875924`, 2026-09-06, "Move image startup and recovery into userspace")

No message body. The diff: `DOLLY_PROCESS_SPAWN_FOREGROUND = 1u << 1` and `/* Foreground owner survives Ctrl-C; its active descendants receive SIGINT. */ DOLLY_PROCESS_SPAWN_INTERACTIVE = 1u << 2`; the kernel's `foreground_pid` and `refresh_foreground` (interruptible = a non-interactive owner, or an interactive owner with a live descendant: the child scan); `-EBUSY` for a FOREGROUND spawn from outside the tree; `dolly_spawn_foreground(path, argc, argv, interactive)`; `/bin/foreground [-i]`; the supervisor's `foregroundRootPid` and page options deleted, the flag read back through `_dolly_process_spawn_flags`; `modules/startup-*.dm` with the `init.slop` that is still today's (`.dollyrc` through `foreground` without `-i`, Pi through `foreground -i`, three attempts, then the recovery shell). The reason is in the docs of the same commit:

> "Foreground and interactive roles are explicit spawn flags, owned by the kernel. Only the current foreground tree can transfer ownership to a child; retirement restores its nearest foreground ancestor. An interactive owner receives terminal Ctrl-C when idle, while its active descendants receive process-directed SIGINT. An ordinary foreground job is itself cancellable. Image-owned init scripts use the ordinary `/bin/foreground` launcher to select these roles; the browser does not recognize Slop, Pi or recovery paths." (`docs/process-model.md` at `3f875924`)
>
> "The supervisor executes the image's ENTRY without selecting programs or recovery policy. Foreground roles live in Wasm process records." (`docs/browser-boundary.md` at `3f875924`)

So the flag replaced a page that knew two program names. "Receives terminal Ctrl-C when idle" meant as input: an interactive owner without children was not interruptible.

### 1.4 Slop learns of Ctrl+C from its child (2026-09-13)

`b547e3c4` "Stop interrupted shell commands and preserve cwd across nested execution", `8888e4f2`, task `20260913-092832-codex-03` ("Ctrl+C stops the remaining interrupted list/pipeline … the interactive prompt remains usable"). Slop was never the target then; it read `WIFSIGNALED`/`SIGINT` from `waitpid` and stopped the list. That path is today's `wait_command` (`src/slop.c:3031-3035`).

### 1.5 The ABI made explicit (`26277ef5`, `d8fa8c47`, 2026-09-30)

`26277ef5`: constants generated from `process.h`, `take_interrupt` declared in the WAT, "The kernel exports exactly its declared contract functions". `d8fa8c47` rewrote the docs to "SIGINT to the foreground tree but spares an interactive owner (the shell)". Audit `20260930-100000-audit-32` (Slop pipelines) recorded the same day: "**Ctrl+C** reaches the whole foreground tree, so every stage gets `SIGINT`" and "Refused by name: `jobs`, `fg`, `bg` (no job control)".

### 1.6 The reverted experiment and the ISIG decision (2026-09-30 to 10-01)

Task `20261001-000500-slop-loop-interrupt`: "`while :; do :; done` typed at the prompt runs forever: an interactive owner without live children is not interruptible … so Ctrl+C reaches Slop as input it never reads. Only a page reload recovers."

Owner decision (2026-10-01): "Termios ISIG, the Unix model. Ctrl+C is SIGINT to the foreground while its terminal has ISIG set and input while a program clears ISIG (raw mode, as Pi's editor and Codex do). Slop's line editor clears ISIG while reading a line and restores it while commands run, so a builtin-only loop stops. This replaces `include/dolly/runtime.h`'s rule."

`ae86e8c0` "Make Ctrl+C follow termios ISIG": the kernel's child scan deleted, `refresh_foreground` publishes interruptible exactly while ISIG is set; `process.h`'s comment became "While the owner has active descendants, Ctrl-C sends SIGINT to them only."; the supervisor's line became `process.interactive && descendants.length ? descendants : [process, ...descendants]` with the comment "Like a job-control shell, an interactive owner's running commands take SIGINT in its place; without any it takes SIGINT itself." (blame: both lines `ae86e8c0`); Slop got its recording handler, the 64-command poll, and the ISIG toggle around each line. Measured in the task: polling the kernel per command cost 8.5x; every 64th command, noise. "Behaviour changes: An interactive owner that keeps `ISIG` now takes SIGINT while it runs no child: the `foreground -i` game entries (classicube-agent, rts-arena, bhop-agent) end on Ctrl+C instead of receiving the key."

Same day: `9f1cdbb5` "Drop the double Ctrl+C force exit" ("one that ignores SIGINT now keeps running, as in POSIX"); `892c163d` the launch-window rule ("Slop does not start a command after an interrupt reached it during the command's preparation"), from the task's gap: "A Ctrl+C pressed right after Enter, while Slop is still launching the command, targets the shell (no running descendant yet) … In Unix the child shares the foreground process group and receives the signal."; `148f77d5` Janis raw mode clears ISIG; `9b3e8c99` SIGALRM, with `ALARM_HANDLED`, the one disposition the kernel is told (`process.h:173-175`).

## 2. What it does today

### 2.1 The two bits

`include/dolly/process.h:178-183`: `INHERIT_ENVIRONMENT = 1`, `FOREGROUND = 2`, `INTERACTIVE = 4` with the one comment "While the owner has active descendants, Ctrl-C sends SIGINT to them only."

Kernel, `spawn_packet` (`src/process-kernel.c:684-803`): any other bit, or INTERACTIVE without FOREGROUND, is `-EINVAL` (`:694-698`); FOREGROUND from a parent that does not descend from the current owner is `-EBUSY` (`:716-718`); the flags are stored (`:723`); FOREGROUND makes the child the owner (`:798-800`) and `refresh_foreground` runs (`:801`). After that the kernel reads only FOREGROUND: `refresh_foreground` (`:180-194`) walks up from `foreground_pid` past retired or non-FOREGROUND records, and publishes `(pid, interruptible)` where interruptible is "running and ISIG set" (`:191-193`); it runs on every spawn, exit, retirement and terminal mode change (`:367, 801, 1531, 2524`). INTERACTIVE is read nowhere in C except validation (`grep` over `src/process-kernel.c`, `src/dolly.c`, `host/*/kernel.c`: lines 696-697 only). It is exported as a number (`dolly_process_spawn_flags`, `:2528-2531`; `abi/dolly-supervisor-0.wat:45,92`).

Supervisor: `#registerProcess` reads it into `process.interactive` (`src/process-supervisor.mjs:221-230`); `#interruptForeground` uses it (`:277`); `#reclamationDeadline` uses it (`:669-673`: an interactive process with a memory of at least 128 MiB gets 500 ms before its retirement is acknowledged, `:697-702`; `docs/process-model.md:263-268`; `test/display-browser.mjs:94-125`).

Who may set them: anything that calls SPAWN with the bits, subject to the two kernel checks. In practice `dolly_spawn_foreground(path, argc, argv, interactive)` (`src/process/runtime-adapter.c:132-140`: stdio mapped 0-2, environ, no deadline), which `/bin/foreground [-i]` wraps (`src/commands/foreground.c:21-22`). The page's root spawn passes FOREGROUND only (`src/runtime-worker.mjs:59`; `supervisor.spawn(arguments, { foreground })`, `:200-202`); the build engine's root spawn passes nothing (`:200`).

### 2.2 The path of a Ctrl+C

1. Page: `host/input/input.mjs:298-299` names the chord (Ctrl+C, no other modifier, keydown). `handleKeyboardEvent` (`:301-344`): a module UI may claim keys; a claim of `"interrupt"` still interrupts (the upload dialog, `host/upload/upload.mjs:15`); otherwise `interruptChord(event) && interruptForeground()` swallows the key, else it is pushed as input (`:333-338`).
2. `terminal.interruptForeground()` (`host/runtime/runtime.mjs:59-65`): reads the mailbox's `foregroundPid` and `foregroundInterruptible`; if both, writes `interruptTargetPid` and increments `interruptSequence`, returns true. "False (ISIG clear) lets the key reach it as input." The same request can come from inside Wasm: byte 3 typed through `buttons@0` (`host/input/kernel.c:147-160`, `dolly_kernel_foreground_interrupt`).
3. Kernel mailbox (`src/dolly.c:28-90`): `dolly_kernel_foreground_publish` writes pid and interruptible; `dolly_process_take_interrupt` consumes one request and returns the target only if it is still the interruptible owner (`:80-90`). The WAT: "Consume the page's latest interrupt request: the targeted PID when it is still the interruptible foreground owner, otherwise zero." (`abi/dolly-supervisor-0.wat:68-70`).
4. Supervisor tick (`:249-258`, 16 ms): `take_interrupt` then `#interruptForeground(pid)` (`:268-280`): descendants are the registered processes whose `parent` chain reaches `pid` (`#descendantDepth`, `:238-247`), excluding retiring ones; targets are `process.interactive && descendants.length ? descendants : [process, ...descendants]`.
5. `#deliverSignal(target, SIGINT)` (`:282-306`): `_dolly_process_signal(pid, 2)`; a process not yet started, or a refused call, is force-exited at once (`:288-290`; kernel `:2547-2548`: "SIGKILL and signals before command entry cannot run userspace handlers"); a parked call (deferred `READ`, `WAIT`, `POLL`, `SLEEP`, `LOCK`) is answered `-EINTR` (`:293-298`); a 500 ms `interruptTimer` is armed (`:299-304`).
6. Kernel `dolly_process_signal` (`:2533-2551`): pending bit, and for a terminating signal an `interrupt_deadline` 500 ms ahead (`:2544-2545`), which parks the parent's EXIT while the child is inside it (`:2335-2343`).
7. Process libc (`src/process/signal.c`): `dolly_process_call` sees `-EINTR` (`:286-303`), issues `INTERRUPT_POLL` (kernel `:2221-2229` hands over one signal, sets `handling_signal`), runs `deliver_pending` (`:93-132`), then `SIGNAL_ACKNOWLEDGE` (`:49-54`; kernel `:2230-2239`); the supervisor clears its timer when the acknowledgement reports nothing pending (`:615-620`). A program in a loop that enters the kernel at least once a millisecond polls through the Worker's fast path (`src/process-worker.mjs:38-41, 97-101`); one that handles cooperatively (QuickJS's interrupt handler, `demos/javascript/quickjs-main.c:35-41`; Slop every 64 builtins, `src/slop.c:195-201`) asks itself.
8. One that never reaches the kernel: the timer fires, `#forceExit` (`:748-755`) records `worker_exited(pid, 130, 2)` and retires the Worker (`worker.terminate()`, `:779`); the kernel marks the subtree exited (`mark_process_exited`, `:351-368`).
9. EXIT with a terminating signal pending becomes a signal exit whatever status was asked (`:2327-2334`: "must not let an otherwise signal-unaware program turn Ctrl-C into an arbitrary failure status").

### 2.3 What `signal.c` does with `SIG_IGN` and with a handler

`deliver_pending` (`:93-132`): `SIG_IGN` → `continue` (`:107`), the loop's `restart` stays 2, the call is retried (`:288-303`); `SIG_DFL` → `dolly_exit_signal(number)` (`:108-113`), an EXIT with the signal; a handler runs with its mask, `SA_RESETHAND`, `SA_NODEFER`, `SA_SIGINFO` (`:114-128`); without `SA_RESTART`, `READ`, `WRITE`, `WAIT`, `POLL`, `SLEEP`, `LOCK` return `-EINTR`, with it `POLL` and `SLEEP` still do (`:298-302`). A handler that leaves by `longjmp`/`siglongjmp` is finished through the jump (`:255-284`, `20261008-002251-handler-longjmp`). The kernel knows none of this except for SIGALRM (`report_alarm_handled`, `:60-64, 77-80, 106`). `test/process-browser.mjs:112-116` pins "Ctrl-C, even pressed twice, honors SIG_IGN" for a program at the prompt; it is a descendant there, the shell spared.

### 2.4 The sparing rule, its two implementations side by side

| | Display terminal | Pseudo-terminal |
| --- | --- | --- |
| Where | `src/process-supervisor.mjs:268-280` (JS) | `host/pty/kernel.c:106-113` with `dolly_kernel_socket_holders(…, foreground=1, …)`, `src/process-kernel.c:2422-2435` (C) |
| Who is signalled | the owner's descendants, by the supervisor's `parent` mirror | every process holding a descriptor of the slave |
| Who is spared | the owner iff it has INTERACTIVE and at least one non-retiring descendant | the holder of which no other holder is an ancestor, iff another holder descends from it (`first && waits`) |
| Key | the spawn flag | descent only; `posix_spawn` under tmux passes no flag (`runtime-adapter.c:537`) |
| Delivery | `#deliverSignal` from `take_interrupt` | `#deliverSignal` from `_dolly_pty_take_signal` (`:262-266`, `ec45edee`) |
| Input or signal | the display's one global mode (`src/dolly.c:21-23, 92-102`) | each pty's own `mode` (`host/pty/kernel.c:26, 109`) |

Where they agree: a script shell in the tree is signalled in both (it descends from the owner; `a095e7d0`). Where they differ: a FOREGROUND owner without `-i` and with children takes SIGINT at the display (`.dollyrc`'s shell, `test/process-browser.mjs:177-189` "cancel"); the top holder of a pty is spared whatever it was spawned with. The kernel's `refresh_foreground` (`:180-194`), which the reflection counts as the second implementation, chooses the owner and the interruptible bit; the supervisor's walk and the kernel's `dolly_process_descends_from` (`:168-178`) run over the same parent links, which `#registerProcess` checks against `_dolly_process_parent` (`:221-224`); the sibling task `20261013-144241-supervisor-mirror` has that question.

`docs/process-model.md:256-262` states the display rule; `:221-224` the pty rule ("Dolly has no process groups to name a foreground with").

## 4. The reflection's claims, checked

**"An interactive owner with running descendants is spared (`process.h:181`)."** True as the comment's text; the comment is `ae86e8c0`'s (2026-10-01), the bit is `3f875924`'s.

**"Implemented twice (`process-supervisor.mjs:275-279`, `process-kernel.c:180-195`)."** Partly. The display rule is in one place, the supervisor. The kernel lines choose the owner (FOREGROUND bit, retirement) and publish the ISIG bit; they spare nobody. Until `ae86e8c0` the kernel did hold a copy of the rule (the child scan in `refresh_foreground`, `3f875924`), and that copy was deleted on 2026-10-01. A second, different rule exists in the kernel for pseudo-terminals, keyed on descent, not on the flag (2.4).

**"A shell's decision about how Ctrl+C reaches it, written as a spawn flag."** Partly. The decision is the parent's, at spawn, about the child: `/bin/foreground -i` is written in the image's script by whoever wrote the recipe; Slop sets nothing about itself (it spawns with flags 0, and cannot ask for the role: `spawn_packet` refuses FOREGROUND from outside the tree and INTERACTIVE without FOREGROUND). What the flag records is not how Ctrl+C reaches the shell (ISIG decides that) but that the owner's commands take it in its place. The same bit also selects the reclamation window (`:671`), which is not a shell's decision at all.

**"POSIX says the same with `SIG_IGN`, which `src/process/signal.c:107` already honours."** Partly, and the "same" needs the two POSIX models spelled out.

- POSIX job control: the terminal has a foreground process group; the driver sends SIGINT to every process of that group (`ISIG`); an interactive shell puts each job in its own group and itself in none of the foreground ones (`setpgid`, `tcsetpgrp`); it therefore never receives the terminal's SIGINT while a job runs, and at its prompt it is in the foreground group and handles SIGINT (bash resets the line). Nothing is ignored; the shell is spared by group membership. Dolly's flag is this membership written as a bit: there are no process groups (`docs/process-model.md:223-224, 371`; Slop refuses `jobs`, `fg`, `bg`, `src/slop.c:3077`), the kernel's tree is the group, and the owner's bit says "not in it while it has members".
- POSIX without job control (`sh` running a script, `sh -c`, a shell started with `set +m`): the shell and its child share the group; both receive SIGINT; the shell ignores or handles it and then decides from the child's wait status, because a child that handled SIGINT and exited normally (an editor, a REPL, `less`) must not count as an interrupted command. bash's `wait_sigint_received` logic is this; dash's is similar. Slop has the second half of that model already (`wait_command`, `:3031-3035`: a child dead of SIGINT or SIGQUIT stops the list) and the first half as a recording handler (`request_interrupt`, `:187-190`).
- `signal.c:107` honours `SIG_IGN` in the process's libc after the kernel delivered: the pending bit, the `EINTR` wake, the 500 ms deadlines in the kernel (`:2544-2545`) and the supervisor (`:299-304`) are armed for every terminating signal regardless of disposition; the ignoring process must reach `INTERRUPT_POLL` and `SIGNAL_ACKNOWLEDGE` within the grace (it does when parked in a call; a tight loop does not and is terminated as if default). Dispositions do not cross spawn ("A child starts with default dispositions and an empty signal mask", `docs/process-model.md:247-249`; Slop's `trap '' INT` refused, `:2581-2583`), so a parent cannot make a child ignore. The kernel is told one disposition, SIGALRM's, for one reason: a default SIGALRM must end a non-polling loop (`process.h:173-175`, `9b3e8c99`).

**"`SPAWN_FOREGROUND` is mechanism (who owns the terminal) and stays."** True of what the code does with it: `foreground_pid`, `-EBUSY`, transfer and restoration (`:716-718, 798-801, 180-187`), the display lease (`docs/display.md:76`), SIGWINCH to the tree (`:337-345`), discard of unread input at exit (`:366`), the published pid the page and the tests read. The reflection does not say that FOREGROUND alone, without INTERACTIVE, makes an owner "itself cancellable" (`3f875924`'s doc), which is what `.dollyrc`'s shell and the editors, games and viewers started without `-i` rely on (`test/process-browser.mjs` "cancel").

**"Not judged by reading: whether Slop can ignore `SIGINT` across its wait cleanly without the flag. Measure that first."** The reading in section 5 narrows what the measurement has to show; section 6 states it.

**"`process.h` and `slop.c` are in the seed."** True (`toolchain/CMakeLists.txt`; `Dollyfile-system-build:111-112` compiles Slop from the staged source); the supervisor and `foreground.c` are not (`cf5d874c`: `foreground.c` is a `SOURCE` of the root recipe).

## 5. What a change would mean, on real cases

"Today" is the code above. "Alternative" is the reflection's: no INTERACTIVE bit; `#interruptForeground` signals the owner and its descendants; Slop ignores SIGINT while it waits (or, equivalently for most of this, keeps its recording handler). Everything below is read, not run.

**(a) `sleep 100` at the Slop prompt, Ctrl+C.** Today: Slop's line ran with ISIG set (`terminal_signals(1)`, `:5255`); the owner is the interactive Slop (`foreground -i /bin/slop`); targets = `[sleep]`; `sleep` dies 130; `wait_command` sees SIGINT, `interrupt_shell` stops the list; the prompt returns with `slop: status 130`. Data used: the flag and the tree. Alternative: targets = `[slop, sleep]`; Slop, parked in `WAIT`, is woken `-EINTR`, polls, runs `request_interrupt` (or ignores), acknowledges within the tick; `waitpid` is retried on `EINTR` (`:2607`); the rest is as today. What it needs: Slop's disposition installed before the spawn (it is, `:5225-5226`) and the acknowledgement inside 500 ms (a parked call is woken at once). What the flag was the only statement of: nothing, in this case.

**(b) `while true; do :; done` in Slop itself, Ctrl+C.** Today: no descendants, so the owner is the target; the 64th builtin polls (`:195-201`) and the shell stops with 130 (`test/slop-browser.mjs`). Alternative: identical; the flag plays no part when there are no descendants. What the alternative needs: Slop keeps a handler, not `SIG_IGN`, outside its waits; so "ignore while it waits" is a disposition switched around every spawn and wait, two `sigaction` calls per command, or one handler for both states (today's).

**(c) Pi or Codex as `foreground -i` ENTRY running a tool, Ctrl+C.** Today, two sub-cases decided by one global terminal mode. Pi's editor is in raw mode (ISIG clear, `quickjs-main.c:899-915`), and the tool's `slop -c` child does not change the mode (only the interactive `interactive()` loop does): the owner is published as not interruptible, the page pushes 0x03 as input, nothing is signalled, and Pi's editor acts on the byte (`pi-browser.mjs:236-242` pins this while a response streams; nothing pins it during a tool). If a `-i` owner has ISIG set while a descendant runs (Codex's sign-in screen if crossterm has not entered raw mode yet; a Janis agent harness that never sets raw mode and spawns a game, `demos/bhop/agent/main.mjs:15`, `demos/rts/spectator/main.mjs:57`), the flag spares the owner and the child takes SIGINT. Alternative: in the raw-mode sub-case nothing changes; in the ISIG sub-case Pi (Janis exits 130 on SIGINT unless a handler is set, `quickjs-main.c:1951-1964`) and Codex would take SIGINT with their tool, which is the outcome `f91e1aef` reverted for ("would end Pi instead of reaching its editor"); the alternative would need each such program to ignore or handle SIGINT while it has a child, and to know when it has one. The `-i` on these 9 rows is the only place that fact is stated.

**(d) Python's REPL from Slop, Ctrl+C at its prompt and during a computation.** Today: Python is a descendant; the owner (Slop, ISIG set, has a descendant) is spared; Python gets SIGINT, its handler raises `KeyboardInterrupt`, the REPL prints a new prompt (`python-browser.mjs:81-88` pins the `signal.pause` form). Python keeps running; Slop never hears of the press. Alternative: Slop gets the same SIGINT; its handler sets `interrupt_requested` (`:188`); the `WAIT` is restarted; when Python later exits normally, `wait_command` sees no signal, but `interrupt_requested` is still 1: at the prompt it is cleared before the next line (`:5254`), but inside a list (`python; echo after`, or a script line, or a `for` body) `spawn_command` reads it as "Ctrl+C that reached the shell while it prepared this command" and returns 130 without starting `echo` (`:3053-3057`, `892c163d`). So the alternative needs the non-job-control shell's rule: clear or discount a SIGINT the child survived, while still honouring one that lands in the launch window; that is the judgement bash makes from the wait status, and the flag is today the only thing that makes the question not arise. Same for `less`, a game that handles SIGINT as quit (`rts-browser.mjs:181`: "SDL may handle interrupted event polling as a clean quit"), and any program whose handler does not end it.

**(e) A program that hangs in a Wasm loop and never polls.** Today: it is a descendant; it gets the pending bit and no wake; 500 ms later `#forceExit` terminates its Worker with 130 (`shell-browser.mjs:161-168`); the owner is untouched. If the owner itself hangs (a `-i` program with ISIG set and no child), it is the target and is terminated the same way. Alternative: the descendant case is identical; the owner-with-child case adds the owner as a target, so a shell that failed to acknowledge within 500 ms (it is parked in `WAIT`, so it acknowledges) would be terminated with its child. Neither model can interrupt a hung process cooperatively; the flag changes only whether the owner's deadline is armed.

**(f) Slop inside a tmux pane.** Today: the pane's shell is spawned by tmux with `posix_spawn` (flags 0, no `-i` possible); the kernel's pty rule spares it by descent (`host/pty/kernel.c:109-112`, `tmux-browser.mjs:63-68`). The display's Ctrl+C never reaches the panes because the server was started beside the shell, not under it (`:111-117`; task point 2). Alternative: the pty rule is already flagless and would stay; the two rules would then differ in the other direction (the pty spares an owner without `-i`, the display would spare none), unless the display rule were rewritten in the pty's shape (the kernel choosing targets by descent, which the reflection's point 3 and the supervisor-mirror task propose). What the pty case shows: a sparing rule without the flag exists and is tested, and it spares the top of the tree whether or not it is a shell.

What the flag is the only statement of, exactly: for the 9 `-i` program rows, that the program is a shell-like owner whose commands take its Ctrl+C; for `foreground -i /bin/slop SCRIPT`, nothing in practice (the script shell is an ancestor of the program it starts through `foreground`, and takes SIGINT when it is the owner with children only in the window between `foreground`'s child exiting and `foreground` itself exiting); for the 32 bare `foreground -i /bin/slop` rows and every recovery shell, that a Ctrl+C the child survived is not the shell's (case d) and that the shell is not a target whose 500 ms deadline is armed (case e).

What would get simpler, as observed: one bit and one `-i` fewer in the contract, the command and 60 recipe rows; `#interruptForeground` becomes "owner and descendants" (or the kernel's list); the reclamation window needs another key (memory size alone, or none). What would move into programs: Slop's wait-status rule for survived interrupts (d); a SIGINT policy in Pi, Codex and the six agent harnesses for the ISIG-set window (c); and the supervisor-mirror question is unchanged (the walk stays, flag or not).

## 6. What could not be found out

- **The measurement the task asks for.** It has to show, in a browser, for Slop spawned by `foreground /bin/slop` (no `-i`) with ISIG set: (1) `sleep 100`, Ctrl+C: the prompt returns with 130 and the next line runs; (2) `python` at its REPL (or `less`, or `/tmp/signals ignore-loop` from `test/fixtures/process-signals.c`), Ctrl+C, then Ctrl+D or `q`, inside a list `python; echo AFTER`: whether `AFTER` runs; (3) the same with the press landing right after Enter (the launch window of `892c163d`): whether the command is cancelled; (4) a pipeline `a | b` where one stage ignores SIGINT; (5) the supervisor's timer on Slop: whether an acknowledgement arrives within 500 ms in every parked state, including `FD_LOCK` and a terminal read with `ISIG` set; (6) Pi and Codex with ISIG set and a running tool (if that state exists: see next point), Ctrl+C: what ends. Each needs a kernel or supervisor build and the `system` image, not a catalog rebuild, except (6).
- **Pi's and Codex's terminal mode while a tool runs.** Not recorded; `pi-browser.mjs` tests raw mode while a response streams only. Whether crossterm has entered raw mode when the sign-in screen is drawn is not recorded; `codex-browser.mjs:13` says only that Ctrl+C leaves the screen.
- **Why `3f875924` has no message body**, and whether the flag's shape was discussed anywhere: no task of 2026-09-06 mentions it; the docs of that commit are the only reasoning.
- **Why some programs get `-i` and others not** (editors and games without, agents with): no recipe comment, no task; the `single-program-images` task describes `-i` without ranking programs.
- **The owner's words on the flag itself**: the ISIG decision is the one owner decision on Ctrl+C; the flag is mentioned in it ("The supervisor still spares an interactive owner while it has running descendants (like a job-control shell)") as kept, not as decided.
- **Whether a process that ignores SIGINT is ever terminated by the 500 ms deadline in practice** (a tight loop with `SIG_IGN` installed): no test; by reading, it is.
- **The cost of the alternative's `sigaction` pair per command**, if "ignore while it waits" is taken literally: not measured; the only related figure is the 2026-10-01 poll cost.
- **Whether the supervisor's mirror and the kernel's tree can disagree** during retirement races: the sibling task's question; this one read only that both walk the same `parent` links.
