### 1.4 The input lease

`dolly_input_acquire` gives "the foreground process or a descendant the lease, one at a time. It then reads every record ... The page sends it every button, pointer presence and a paste as text records." (`docs/input.md:27-30`; `host/input/kernel.c:189-203`). That is the recorded answer for a program that wants the pointer: a graphics program (games, Slopyard, Wine) takes the lease and reads records. A terminal program does not: the lease stops the terminal's decoder (`host/input/kernel.c:122`, `lease_generation == 0`), so a program that took it to see the mouse would lose its keys as terminal bytes too. The test at `test/terminal-browser.mjs:228-238` pins that a lessee gets every pointer and scroll record. No task proposes the lease for a TUI.

### 2.2 What the terminal does when a program sets a mouse mode

`CSI ? 1000 h` (and 9, 1002, 1003, 1005, 1006, 1015, 1016) is parsed by Ghostty's VT stream and recorded in the terminal's flags: `stream_terminal.zig:1609-1640` sets `terminal.flags.mouse_event` to `.x10`, `.normal`, `.button`, `.any` or `.none`, and `terminal.flags.mouse_format` to `.utf8`, `.sgr`, `.urxvt`, `.sgr_pixels` or `.x10`. `display.c` never reads them: `grep -n "MOUSE\|mouse" src/ghostty/display.c` is empty. A press is a selection press whatever the mode. A `DECRQM` query of 1000 is answered by Ghostty from the same flags (the program is told the mode is set).

### 2.3 Ghostty's VT library: what it records and what it can encode

### 2.4 The alternate screen and the wheel

- `handle_scroll` calls `ghostty_terminal_scroll_viewport` whatever screen is active. Ghostty: "If the terminal has no scrollback (e.g. the alternate screen is active), the viewport always remains on the active area" (`terminal.h:238-241`). So in `less`, nvim, tmux and Pi the wheel does nothing today, as the tmux-use task measured ("the wheel scrolls nothing").
- Alternate scroll (`CSI ? 1007 h`, default on in Ghostty's table) is the app's: Ghostty's `Surface.zig:3565-3596` sends `ESC [ A`/`ESC [ B` (or `ESC O A`/`B` under DECCKM) per wheel step when "(1) alt screen (2) no explicit mouse reporting and (3) alt scroll mode enabled", and clears the selection first. Nothing in `display.c` does this; no task mentions 1007.
- Under mouse reporting, Ghostty's app sends wheel steps as button 4/5 presses and does not move the viewport (`Surface.zig:3602-3618`).

### 2.5 A program on a pseudo-terminal slave: tmux

tmux holds the display's terminal in raw mode and reads it byte by byte through `FD_READ`'s terminal branch (`src/process-kernel.c:1153-1168`; the line-discipline investigation §2.1). A mouse report written into `pty_response` would arrive in that read like a key. tmux parses `ESC [ M` and `ESC [ <` SGR reports in `tty-keys.c:1204-1210` (`tty_keys_mouse`). What it asks for when `mouse` is on: it clears all four modes and sets `?1006h` plus `?1000h ?1002h ?1003h`, `?1000h ?1002h` or `?1000h` by what its panes want (`tty.c:904-919`; `server-client.c:2294-2306`), only if the terminal description has `kmous` (`tty_term_has(term, TTYC_KMOUS)`). To a pane it forwards an event only if the pane's program set a mouse mode ("`if ((s->mode & ALL_MOUSE_MODES) == 0) return (0);`"), in SGR only if the program asked for 1006 and the outer terminal sent SGR, else UTF-8 or legacy (`input-keys.c:725-795`); the option's text: "Applications inside panes can use the mouse even when 'off'." (`options-table.c:946-948`). The pane program's `?1000h` is recorded per pane by tmux's own parser (`input.c:2053-2061`, `1956-1969`), answered to `DECRQM` (`:1689-1705`).

## 4. Each claim of the task as filed, checked

**"tmux asks for the reports (`mouse` is on in this build) and gets none."** True. `-DTMUX_MOUSE=1` (`Dollyfile-tmux:65`) is upstream's knob for the `mouse` default (`options-table.c:945`); `tty.c:904-919` sends the requests; `display.c` produces none (2.2).

**"The display's terminal keeps pointer and scroll records for itself, selection and scrollback ... and under a full-screen program it has no scrollback to show."** True (`ring.c:13-18`; `display.c:880-886`; `terminal.h:238-241`).

**"Where it lives: `src/ghostty/display.c`, the display library, which every image is built against (an image input). So it rides a catalog round."** True in effect, with the mechanism stated: programs do not link the plugin; `ghostty-build` compiles `lib_vt.zig` to C and `display.c` with it into `/usr/lib/libdisplay.so` (`Dollyfile-ghostty-build:38-49`; `docs/display.md:103-106`), `display` stands on `ghostty-build` (`Dollyfile-display`), `system` copies the plugin, and 21 recipes stand on `system` by pin, 33 on `system-tools`/`system-build`. A change repins that chain. The page also sends the terminal only the primary button (2.1), so a change that wants other buttons or bare motion touches `host/input/input.mjs` as well, which is page code, not an image input.

**"Not known: whether Ghostty's terminal library already tracks the mouse modes a program sets and can encode a report."** Now read: it tracks them (`stream_terminal.zig:1609-1640`), exposes them (`GHOSTTY_TERMINAL_DATA_MOUSE_TRACKING`, `GHOSTTY_TERMINAL_DATA_MODE`) and has the encoder with `setopt_from_terminal` (2.3). "Then this is a few lines in `display.c`" is a size judgement not made here; what would have to exist is listed in section 5.

**"What a user's selection does while a program has the mouse (terminals hold Shift for it)."** The convention, read in Ghostty's own app code (not in the library the plugin uses): `mouse-shift-capture` defaults to `false` ("Enable or disable mouse reporting. When set to `false`, mouse events will not be reported to terminal applications even if they request it", `Config.zig:969-981`); `mouseShiftCapture` honours the terminal's own request first (`XTSHIFTESCAPE`, `flags.mouse_shift_capture`, `Terminal.zig:121`, `stream.zig:2364`) then the config (`Surface.zig:3752-3778`); on a press under reporting "If we have shift-pressed and we aren't allowed to capture it, then we do not do a mouse report", otherwise the selection is cleared, the gesture reset and the press reported (`:3933-3960`); motion the same (`:4639-4656`); a wheel step under reporting clears the selection and is reported (`:3557-3561, 3602-3618`). The same rule is in the config comment "Shift overrides mouse 'grabbing' in the window, taken from Kitty." (`:4640`). Ghostty also has a `mouse-reporting` config and a `toggle_mouse_reporting` keybind (`Config.zig:971-981`). xterm's rule is the same by convention; it was not read here.

## 5. What a change would mean, on real cases

Observations only. "A change" means: `display.c` asks Ghostty whether tracking is on, encodes a pointer or scroll record with the mouse encoder when it is (Shift excepted, if the convention is followed), writes the bytes into `pty_response` as it writes a cursor report, and runs the selection gesture otherwise. "Today" is section 2.

Where the decision would be made: `decode_record` (`display.c:880-886`), per record, on the display's tick, with capacity 0 for output (`ring.c:17`), so the bytes would go through `terminal_write_pty`/`read_replies` (`:236-246, 656-667`), the channel the terminal's replies already use; `fill_terminal_input` reads replies before the next record (`host/input/kernel.c:108-111`). Which bytes: the encoder's, by the recorded format (`\e[<b;x;yM`/`m` under 1006, `\e[M` plus three bytes otherwise). Which API: `GHOSTTY_TERMINAL_DATA_MOUSE_TRACKING` or `DATA_MODE`, `ghostty_mouse_encoder_setopt_from_terminal`, `ghostty_mouse_event_set_*`, `ghostty_mouse_encoder_encode`; for 1016 the `SIZE` option with cell geometry `display.c` already has (`cell_width`, `padding_x`, `framebuffer_height`, `:813-818`). Image input: `display.c` (the chain in section 4). Page: `input.mjs:390, 437, 451-453` decide which buttons and motion reach the ring without a lease; the record already carries the button (`flags >> 8`) and modifiers.

**(a) tmux with two panes.** Today: a click lands in Ghostty's selection; the text goes to the pane that had the focus; the wheel does nothing (tmux-use `:129-136`). With reports: tmux's `tty_keys_mouse` reads the press; with `mouse` on, a click selects the pane, a drag on the border resizes, the wheel over a pane enters copy mode and scrolls it (tmux's own bindings, upstream). A drag inside a pane would be tmux's copy-mode selection, not the display's, and Ctrl+Shift+C would copy nothing unless Shift bypassed the report. The tmux test's `waitText` gesture would then be a click and drag reported to tmux (3, (e)). The requests arrive only if `xterm-256color`'s description has `kmous`; `TERM` is `xterm-256color` (`docs/display.md:56`), and the tmux-use task says the requests were sent, so it has.

**(b) nvim.** Today: a click selects text in the display, the wheel moves nothing (alternate screen). With reports under `mouse=nvi`: nvim places the cursor on a click and scrolls on the wheel; the display's selection is gone while nvim runs unless Shift. Nvim's test does not read text while nvim runs (3).

**(c) `less` under git.** `LESS=FRX` sets no `--mouse`: no request, so nothing changes: a drag selects, the wheel does nothing (alternate screen, `less` uses `ti`/`te`). Only alternate scroll (2.4), if added, would make the wheel move `less` and nvim; that is a separate mode (1007), on by default in Ghostty's table, and would send arrow keys to any full-screen program that did not ask for the mouse, `less` and `man` included.

**(d) A program that never asks: Slop's prompt, `cat`.** `flags.mouse_event` stays `.none`; the decision falls to today's branch; selection and scrollback exactly as today. The 61 test files that read the shell's screen are in this case.

**(e) The test harness's screen reader.** `visibleTerminalText` pushes press, drag, release with `modifiers` 0 (`terminal-text.mjs:32-35`). While a program has the mouse, each would be a report to the program, no selection would be made, and the reader would throw "timed out waiting for terminal selection publication" after its four attempts (`:24-38`). Affected: the tmux test (`waitText` while tmux is attached), Pi's test only if `tuiMode` changed, Emacs's and nvim's tests only in `open()`'s prompt wait (at the shell, before the program). A harness that pushed Shift (`modifiers: 1`) would keep reading screens if `display.c` followed Ghostty's Shift rule; the record format already carries the bit. Nothing of this is measured.

**(f) The phone.** A finger's drag is scroll records (`input.mjs:430-433`); a tap pushes no pointer record (`:391-398`). Under a reporting program a drag would become wheel reports (button 4/5 presses, as Ghostty's app does) and a tap nothing; a click to select a tmux pane would have no finger equivalent. The pinch stays Ctrl+=/Ctrl+-.

**(g) A program on a pty slave inside tmux that asks for the mouse.** tmux records the pane's request (`input.c:2053-2061`) and forwards the display's reports per pane only when the pane asked, in the pane's format (`input-keys.c:725-795`). The display library would not know of the pane; it would report to tmux by tmux's own mode. With `mouse` off in tmux, tmux still asks the outer terminal for what its panes ask (`server-client.c:2294-2306`).

**(h) What a forced termination leaves.** The plugin's terminal state survives a program's end ("terminal state survives foreground replacement", `docs/display.md:39-40`); nothing in `display.c` reads the foreground or resets a mode on a change of it (`grep foreground src/ghostty/display.c` hits colours only). A program ended by the 500 ms rule with 1000h set would leave the terminal reporting: the next shell prompt would get `\e[<0;…M` as input on every click. The same is true today of kitty keyboard flags and the alternate screen left behind by a dead program (no task records a complaint); the terminal mode flags (`ISIG`) have the same gap (line-discipline §2.6: "A process ended by force leaves what it set"). Ghostty offers `GHOSTTY_TERMINAL_OPT_MODE` to set a mode and `ghostty_terminal_reset` (`terminal.h:1825-1864`); `refresh_foreground` (`src/process-kernel.c:180-194`) runs at every exit and is the kernel's one place that sees the owner change, but it does not reach the plugin. Who would reset is undecided in the code.

What today's behaviour is relied upon by, exactly: the 61 screen-reading test files through the gesture (`src/terminal-text.mjs`); `test/terminal-browser.mjs:57-86, 173-178`; the clipboard path (`docs/browser-boundary.md:207`); the phone's drag-to-scroll; the kernel's discard rule for pointer records at retirement (`ring.c:60-67`, `test/display-browser.mjs` retirement case); Pi's `tuiMode: "regular"` (chosen because of it); tmux's README limit (`demos/tmux/README.md:78-80`).

- Why `-DTMUX_MOUSE=1` was set (no record).
- The cost of one encoder call per drag sample on the 16 ms tick, and whether a report for every motion sample under 1003 would fill `pty_response` (512 KiB) before a slow reader drains it.
